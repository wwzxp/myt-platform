## 0. 文件放置规范

### 代码文件

新增代码文件时，**必须先阅读项目现有目录结构**，按以下原则放置：

1. 同类文件放在同一目录下，与现有同类文件并排
2. 不得在项目根目录随意新建文件，除非项目惯例如此
3. 新建目录前确认是否有合适的现有目录可以归入
4. 文件命名与同目录下现有文件的命名风格保持一致（大小写、分隔符、前后缀）

> 放置前先执行：`read <项目根目录>` 了解目录结构，再决定放哪里。

### 目录与文件命名规范

**通用原则**：命名风格与项目现有文件保持一致，优先参考同目录下已有文件的命名方式。

#### 正式功能文件（不带时间戳）

正式功能代码、模块、配置文件使用简洁描述性名称，**不加时间戳**：

```
user_service.py        ✅
config.json            ✅
data_parser.py         ✅
user_service_20260714_153045.py  ❌ 正式文件不加时间戳
```

#### 测试脚本（带时间戳）

测试脚本、调试脚本、验证脚本文件名**必须带时间戳**，格式 `YYYYMMDD_HHMMSS`：

```
test_login_20260714_153045.py
verify_api_20260714_090012.py
debug_parser_20260714_210305.py
check_data_20260714_080000.py
```

#### 资源文件、临时文件（带时间戳）

抓包数据、测试数据、临时输出、实验性脚本等资源文件**必须带时间戳**：

```
capture_20260714_153045.json
sample_data_20260714_090012.csv
output_20260714_210305.txt
draft_20260714_080000.py
```

#### 目录命名与归类

1. 与项目现有目录命名风格一致（全小写/驼峰/下划线）
2. 正式功能目录不加时间戳：`services/`、`utils/`、`models/`
3. 临时目录、实验目录可加时间戳后缀：`test_20260714_153045/`、`temp_20260714_153045/`

**归类原则（重要）**：

- 文件必须按功能或用途归入对应分类目录，**严禁将大量文件堆放在同一目录下**
- 新增文件前先判断归属，放入最匹配的现有目录；无合适目录时才新建
- 测试文件、资源文件较多时，**必须建立分类子目录**，不得全部平铺

**测试文件分类目录示例**：

```
tests/
  login/            ← 登录相关测试
    test_login_20260714_153045.py
    test_logout_20260714_160000.py
  api/              ← 接口测试
    test_user_api_20260714_153045.py
    test_order_api_20260714_154500.py
  data/             ← 数据验证测试
    verify_data_20260714_153045.py
```

**资源文件分类目录示例**：

```
resources/
  capture/          ← 抓包数据
    capture_20260714_153045.json
  sample/           ← 样本数据
    sample_user_20260714_090012.csv
  output/           ← 输出结果
    output_20260714_210305.txt
```

> 时间戳格式统一使用 `YYYYMMDD_HHMMSS`，放在文件名末尾、扩展名之前。

### 索引文件

索引 md 文件的标准位置（按优先级查找）：

1. 项目根目录：`INDEX.md`
2. 文档目录：`docs/INDEX.md` 或 `docs/index.md`
3. 项目已有的文档汇总文件（如 `README.md` 中的文件清单章节）

**查找逻辑**：
- 任务开始前先检查以上路径是否存在索引文件
- 存在则直接使用，不得另建新的索引文件
- 不存在则在项目根目录创建 `INDEX.md`，并在第一次任务中初始化结构

**索引文件初始结构**（首次创建时使用）：

```markdown
# 项目索引

## 目录结构
<!-- 项目主要目录和文件说明 -->

## 模块说明
<!-- 各模块职责和对外接口 -->

## 变更记录
<!-- 按时间顺序排列，最新记录在最前面 -->
<!-- 格式：YYYY-MM-DD HH:MM:SS | 类型 | 文件路径 | 说明 -->

| 时间 | 类型 | 文件/模块 | 说明 |
|------|------|-----------|------|
| 2026-07-14 15:30:45 | 新增 | `src/user_service.py` | 用户服务模块，负责登录注册 |
| 2026-07-14 09:00:12 | bug修复 | `src/parser.py` | 修复空字符串导致的崩溃问题 |
| 2026-07-13 20:15:00 | 新增目录 | `tests/login/` | 登录相关测试文件目录 |
```

**变更记录填写规范**：
- 每次新增文件、修复 bug、新增目录，必须在变更记录中追加一条
- **按时间倒序排列**：最新记录放在表格最上方
- 时间精确到秒，格式：`YYYY-MM-DD HH:MM:SS`
- 类型固定为：`新增` / `修改` / `删除` / `bug修复` / `新增目录`
- 说明简洁描述改动内容，一句话为准

## 1. 文档与注释同步更新

### 执行顺序

**任何代码修改或新增，必须按以下顺序完成文档同步：**

1. **前置：定位影响范围**
   - 调用 `recall` 查阅 Hindsight，确认是否有与本次修改相关的历史决策
   - 读取索引文件（`INDEX.md`），找到受本次修改影响的相关文档和模块条目

2. **执行更新**
   - 更新相关文档文件（设计文档、接口文档、使用说明等）
   - 更新代码文件内的注释（函数注释、模块注释、关键逻辑注释）
   - 若模块职责或对外接口有变化，同步更新索引文件的 `## 模块说明` 章节

3. **收尾：同步知识图谱**
   - 在索引文件 `## 变更记录` 中追加本次变更记录（含时间戳）
   - 若本次涉及重要设计决策、架构选型或踩坑记录，调用 `retain` 保存到 Hindsight

### 知识图谱维护

知识图谱由两部分共同构成：

- **索引文件**（文件/模块级）：记录文件位置、模块职责、调用关系，是项目结构的导航地图
- **Hindsight 记忆**（决策级）：记录技术选型原因、历史踩坑、跨会话的重要决策

维护规则：
- 新增函数/模块时，在索引的 `## 模块说明` 中记录其用途和调用关系
- 修改函数/模块时，同步更新索引中引用该模块的所有描述
- 确保文档描述与代码实现始终一致，不得出现文档与代码不符的情况
- 重要决策必须 `retain`，避免压缩或跨会话后遗失

### Hindsight retain 判定标准

满足以下任一条件，必须调用 `retain`：

**重要设计决策**
- 在两种及以上方案中做了选择，且选择原因不在代码里体现
- 决策影响超过 1 个文件或模块
- 决策涉及性能、安全、兼容性等非功能性考量

**架构选型**
- 引入新的框架、库或工具，并有选型理由
- 确定模块边界、数据流向、接口契约
- 放弃某个方案，且放弃原因需要记录

**踩坑记录**
- 排查时间超过 15 分钟的 bug
- 某个库/API 的非显而易见行为或已知 bug
- 环境配置、依赖版本相关的隐性问题
- 边界情况导致的问题，文档里没有提及的

**用户明确要求**
- 用户说"记住这个" / "记一下" / "下次别忘了"

**不需要 retain 的**
- 单文件内的小决策（索引文件已记录）
- 显而易见的实现细节
- 临时调试信息

> 代码改了文档没更新，视为任务未完成。
> 知识图谱（索引 + Hindsight）是项目的长期资产，每次任务都要维护。

## 2. 代码与注释风格一致性

### 开始前：确认风格基准（按顺序执行）

1. **调用 `recall`**：查阅 Hindsight，确认是否有该项目的风格约定记录
2. **读取项目风格文档**：读取项目根目录的 `STYLE.md`，获取命名规范、注释格式、代码组织约定
3. **读取本次涉及的代码文件**：阅读本次任务需要修改或新增的相关代码文件，理解已有接口签名、调用关系、参数约定

> 第2步和第3步缺一不可：风格文档告诉你**怎么写**，涉及代码文件告诉你**写什么**。
> 只看风格文档不看已有代码，接口签名一旦写错，调用方全部失效。

### 边界情况

- **`STYLE.md` 不存在**：读取项目主要功能文件（2-3个核心文件）推断风格，推断结果 `retain` 到 Hindsight 并提示用户补建 `STYLE.md`
- **`STYLE.md` 存在但 Hindsight 无记录**：读取后将核心约定 `retain` 保存，后续会话直接 `recall` 获取，无需重复读文件
- **风格判断有歧义**：以 `STYLE.md` 为准；`STYLE.md` 未覆盖的细节，以当前文件已有代码为准

### 执行：风格一致性要求

1. **项目整体风格一致**：命名规范、文件组织、模块结构与 `STYLE.md` 及现有代码一致
2. **文件内风格一致**：缩进、空行、括号、注释格式与当前文件已有代码一致
3. **注释风格一致**：注释语言、格式、详细程度与文件已有注释风格一致
4. **接口一致**：新增或修改函数/方法时，签名风格、参数命名、返回值约定与调用方保持一致

> 不得引入与 `STYLE.md` 或现有代码不一致的新风格、新约定或新格式。

## 3. 索引 md 文档维护

> 本节是索引维护的完整触发清单。第1节第3步的"追加变更记录"是其中一种场景的落地步骤，两者不冲突。

**前提：项目必须先建立索引 md 文档（如 `INDEX.md` 或 `docs/index.md`），再执行以下规范。**

### 触发场景：以下情况必须更新索引

1. **新增文件**：在 `## 目录结构` 中登记文件路径和用途，在 `## 变更记录` 追加一条
2. **新增模块/功能**：在 `## 模块说明` 中描述模块职责和对外接口，在 `## 变更记录` 追加一条
3. **修改文件功能/接口**：在 `## 模块说明` 中更新该模块的描述，在 `## 变更记录` 追加一条
4. **修复 bug**：在 `## 变更记录` 追加一条，记录 bug 位置、原因、修复方式
5. **删除文件或模块**：在 `## 目录结构` 和 `## 模块说明` 中移除或标记对应条目，在 `## 变更记录` 追加一条
6. **更新 `STYLE.md`**：在 `## 目录结构` 中同步更新 `STYLE.md` 的说明，在 `## 变更记录` 追加一条

### 更新格式

所有变更记录按第0节定义的格式填写：

- 时间精确到秒：`YYYY-MM-DD HH:MM:SS`
- 倒序排列：最新记录在表格最上方
- 类型固定为：`新增` / `修改` / `删除` / `bug修复` / `新增目录`
- 说明一句话为准，简洁描述改动内容

### 索引不存在时

任务开始前先按第0节定义的初始结构创建 `INDEX.md`，再执行当前任务。

> 索引文档是项目的导航地图，必须与项目实际结构保持同步。
> 格式规范和初始结构详见第0节「索引文件」章节。

## 4. 文件编辑规范

**文件只能编辑，不能整体重写。**

### 执行顺序

1. **先读文件**：编辑前必须读取目标文件，了解当前内容、结构和需要修改的具体位置
2. **定位改动点**：明确需要新增、修改或删除的具体行或代码块，不得凭记忆操作
3. **最小化编辑**：只改动需要改动的部分，不得触碰无关内容

### 禁止行为

- **禁止整体重写文件**：不得用完整新内容覆盖整个文件，即使改动较多也要逐段编辑
- **禁止未读先改**：不得在未读取文件当前内容的情况下直接编辑
- **禁止凭记忆操作**：文件内容可能已被其他任务修改，每次编辑前必须重新读取最新状态

> 整体重写会丢失其他未涉及部分的改动，且无法保证风格和内容与现有文件一致。
> 读了再改，是最基本的文件操作准则。

## 5. 任务完成输出规范

每次任务完成后，必须输出两张表格。格式以实际情况为准，不强制固定列数。

### 改动清单

**必填列**（每次都要有）：

| 文件/模块 | 操作类型 | 修改内容 |
|---|---|---|

**按实际情况追加列**：

| 可选列 | 什么时候加 |
|---|---|
| 影响范围 | 改动涉及调用方或跨文件依赖时 |
| 回滚方案 | 改动风险较高、涉及核心逻辑时 |
| 关联文档 | 有对应文档需要同步时 |
| 备注 | 有特殊说明或遗留问题时 |

- **操作类型**：`新增` / `修改` / `删除` / `bug修复`
- **修改内容**：一句话简述，简单改动写简单，复杂改动可稍详细
- 改动少（1-2个文件）可以简表；改动多（5个以上）需完整列出每个文件

### 完成核对清单

| 检查项 | 状态 |
|---|---|
| 相关文档与注释已同步 | ✅ / ❌ / N/A |
| 索引 md 已更新 | ✅ / ❌ / N/A |
| 代码风格与项目一致 | ✅ / ❌ / N/A |

- **N/A** 需注明原因，例如：`N/A（纯文档修改，无代码变动）`
- 有任何一项为 ❌，任务未完成，必须补齐后重新输出

### 不同任务类型示例

**简单 bug 修复**（精简表）：

| 文件/模块 | 操作类型 | 修改内容 |
|---|---|---|
| `src/parser.py` | bug修复 | 修复空字符串导致崩溃的问题 |

| 检查项 | 状态 |
|---|---|
| 相关文档与注释已同步 | N/A（逻辑修复，无接口变化） |
| 索引 md 已更新 | ✅ |
| 代码风格与项目一致 | ✅ |

**新增功能**（完整表）：

| 文件/模块 | 操作类型 | 修改内容 | 影响范围 |
|---|---|---|---|
| `src/user.py` | 新增 | 新增登录校验函数 | `api/login.py` |
| `tests/login/test_login_20260714_153045.py` | 新增 | 登录功能测试用例 | — |
| `docs/api.md` | 修改 | 新增登录接口说明 | — |
| `INDEX.md` | 修改 | 新增 user.py 条目 | — |

| 检查项 | 状态 |
|---|---|
| 相关文档与注释已同步 | ✅ |
| 索引 md 已更新 | ✅ |
| 代码风格与项目一致 | ✅ |

> 两张表格是任务完成的标志，缺少表格视为任务未结束。
> 格式服务于内容，根据任务复杂度灵活调整，不必拘泥固定模板。

## 6. 禁止自行偏离用户要求（强制）

### 执行顺序

**任何偏离用户已确认方案的操作，必须先问，不得自行决定后默默执行。**

遇到阻塞或需要偏离时，按以下顺序：

1. **立即停止**当前操作
2. **说明**阻塞点、原因、已尝试的方法
3. **给出**可选方案及各自代价
4. **等待**用户决定

### 必须问的情况（非穷举）

| 类型 | 例子 |
|---|---|
| **删除/裁剪用户要求保留的东西** | 用户说「依赖 dsh 基座」，却删掉 `tsconfig.base.json` 的 `paths` 映射 |
| **改变用户已确认的方案** | 用户选「甲」，执行中遇到困难自行改成「乙」 |
| **绕过障碍的降级处理** | 源码跑不起来 → 自行改 `package.json` 指向、改源码、加兼容层 |
| **对配置/依赖/构建脚本的临时修改** | 哪怕「先改回来恢复可安装状态」这种看似无害的 |
| **猜测性补全** | 用户没说的字段、默认值、兜底逻辑，自行补上 |
| **引入用户未要求的抽象或依赖** | 加缓存层、加重试、加适配层、装新包 |

### 判定标准

> 问自己：**如果用户看到我这一步操作，会不会说「我没让你这么做」？**
> 会 → 先问再做。

### 违反后的处理

已造成的偏离**立即主动报告**，说明改了什么、为什么、如何恢复。不得等用户发现。

### 禁止的借口

- ❌「这是为了让它能跑起来」
- ❌「这是明显的技术必要」
- ❌「用户应该会同意」
- ❌「先做，做完再告诉用户」

**上述任何一条都不成立。阻塞就停下问。**
