## 一、两级判定

```
┌─ L1  XML + 关键词 ────────────────────────────────┐
│  取 mCurrentFocus + uiautomator dump               │
│  → Activity.markers 命中？ → 直接定案（毫秒）        │
│  → 页面关键词（中英文）命中？→ 定案（约 2.3s）        │
└───────────────────────────────────────────────────┘
                     ↓ 没命中 / 打平
┌─ L2  截图 + 读字 + 关键词 ─────────────────────────┐
│  截图（50% 缩放）→ MiniCPM-V 4.6 读字（约 7s）       │
│  → 用同一套关键词匹配（0ms）                        │
└───────────────────────────────────────────────────┘
                     ↓ 仍没命中
                  unknown（交等待/重试/人工补规则）
```

**要点：模型只负责「读字」和「补对齐表」，不做页面判断。**
常规判断永远是确定性的文字匹配。

## 二、每级用什么信号

| 级别 | 输入 | 判据 | 耗时 | 失败去向 |
|---|---|---|---|---|
| L1-a | `mCurrentFocus` | `Activity.includes(marker)` | 毫秒 | L1-b |
| L1-b | uiautomator XML 的 `text` / `content-desc` | 页面关键词命中数最多且领先 | ≈2.3s | L2 |
| L2 | 截图（50%） | 4.6 读出的文字 → 同一套关键词 | ≈7s（同图重复 1–3s） | unknown |

## 三、关键词规范（页面表里填）

| 规则 | 说明 | 反例 |
|---|---|---|
| **选独有词** | 只在某个页面出现的词 | ❌「全部」「照片」——几乎每页都有 |
| **不选内容词** | 用户发的文案会变 | ❌「秋冬跑步」「宝石女孩」 |
| **每页 ≥2 个** | 互相印证 | — |
| **允许错字** | OCR/机型差异 | 写「草稿箱」同时容忍「算辑箱」；写「成片」不用「一键成片」 |
| **中英文都写** | App 可能切英文 | `home`：`首页, 市集, 发现, Home, Explore` |
| **避免跨页重复词** | 如「草稿箱」在个人主页也有 | 个人主页改用「笔记」「收藏」「赞过」 |

示例（小红书）：

| 页面 | 关键词 |
|---|---|
| `album` | 实况图, 全屏图, 草稿箱 |
| `image-editor` | 滤镜, 贴纸, 拼图, 标记, 调节 |
| `review` | 成片, 下一步 |
| `profile` | 笔记, 收藏, 赞过 |
| `home` | 关注, 发现, 同城, 首页, 市集 |

## 四、已知边界（必须写死，别指望模型）

| 情况 | 能不能识别 | 正确做法 |
|---|---|---|
| 同布局、只有内容不同（feed 不同位置） | **应判为同一页** | 不要当两页处理 |
| 同 Activity、不同 tab | ❌ 文字完全相同，关键词分不开 | **视为同一页面**（通用工具不为此设特例） |
| 纯图片页（抓到 0 个文字） | L1 失效 | 走 L2 |
| 界面文字被截断/图标化 | 部分失效 | L2 + 关键词，仍不行报 unknown |

## 五、运行参数（本机实测最优）

```
llama-server（用 ollama 自带的那份，主线不支持 minicpmv4_7）
  -m <MiniCPM-V 4.6 模型 gguf>
  --mmproj <MiniCPM-V 4.6 投影层 gguf>
  --load-mode mmap -nr -t 12 -ngl 0 -c 2048 -b 2048 -ub 1024 -fa on
```

| 项 | 值 | 依据 |
|---|---|---|
| 截图缩放 | **50%** | 30% 读不了工具栏；75% 全对但慢一倍；100% 无额外收益 |
| 读字提示词 | 「完整列出截图上的所有文字，不要遗漏，不要编号」 | 少这句模型会漏 |
| 判定提示词 | 附「文字是 OCR 结果，可能有错字，按意思最接近的判断」 | 不加会把相册判成个人页 |
| 不用 | 35B-A3B | 判断力强但 14–127s，只用于离线核对 |

## 八、跨语言：词表只维护中文（2026-11-01 定稿）

### 结论：加一个「对齐」环节，不让模型判断

```
中文词表（唯一数据源）
      ↓
【跨语言对齐】← 模型只做这一个任务：英文词 ↔ 中文词
      ↓
对齐表 { Crop→裁切, Likes→赞过, Market→市集, … }（可审查、可缓存）
      ↓
确定性字符串匹配 → 页面 id
```

**对齐一次，之后纯查表，0 成本。**

### 实测（MiniCPM-V 4.6 文本模式）

| 方案 | 准确 |
|---|---|
| 让模型直接判断页面（中文词表 vs 英文文字） | 3/5 ❌ 会编理由 |
| **先对齐再匹配** | **5/5 ✅** |

对齐表 31 条、4 秒生成，无错词。五个用例：

| 用例 | 译出中文 | 判定 | 得分 |
|---|---|---|---|
| 相册 | 全部/视频/照片/实况图/全屏图/草稿箱 | album | 6 |
| 图片编辑 | 滤镜/文字/贴纸/裁切/标记/调节/拼图 | image-editor | 7 |
| 图片预览 | 选择/自动编辑/下一步 | review | 1 |
| 个人主页 | 笔记/收藏/赞过/草稿箱/… | profile | 4 |
| 首页 | 关注/发现/同城/搜索/首页/市集/消息 | home | 6 |

### 为什么对齐比判断可靠

| 让模型判断 | 让模型对齐 |
|---|---|
| 输出自由，会编造未给出的词 | 输出被约束为 `英文=中文` |
| 错了无法审查 | 对齐表可人工校对 |
| 每次都要跑 | 一次生成，本地缓存 |

### 运行时规则

| 界面语言 | 处理 |
|---|---|
| 中文 | 直接匹配，不查表 |
| 英文/日语等 | 先查对齐表转中文，再匹配 |
| 对齐表缺词 | 该词作废，靠其他词命中；不影响判定 |

### 限制

- 一词多义：`Following` / `Followers` 都会译成「关注」（影响小，都是共有词）；
- 未登记的新词转不出 → 需重新跑一次对齐补齐。

### 已实现（2026-11-01）

| 模块 | 内容 |
|---|---|
| `keyword-align.ts` | `buildAlignPrompt` / `parseAlignTable` / `translateTerms` / `looksChinese` |
| `keyword-align-store.ts` | `AlignCache`（内存+落盘）、`loadAlignTable` / `saveAlignTable` |
| `page-guard.ts` | `PageSpec.keywords`；`resolveByKeywords`（领先才判，打平→unknown）；`currentPage` 接入三级判定 |
| `flow-xhs-publish/pages.ts` | 11 个页面补齐中文关键词 |

### 判定顺序（最终）

```
mCurrentFocus → Activity.markers          毫秒
      ↓ 不中
uiautomator 文字 → contentMarkers（全中）   约 2.3s
      ↓ 不中
关键词打分（原文）
      ↓ 全 unknown
查对齐表翻译 → 关键词再打分
      ↓ 仍 unknown 且给了模型
自动补表（只补缺失词）→ 再打分 → 落盘
      ↓
  unknown
```

### 不做语言判断（实测教训）

不要用「CJK 字符占比」判断界面语言：英文版小红书的 XML 里混着大量中文帖子文案，
占比算出来是「中文」，于是跳过翻译 → unknown。
正确做法是**先原文、不中再翻译**，完全不需要语言检测。

### 验证结果

| 场景 | 结果 |
|---|---|
| 真实 XML：中文首页 | home（原文路径）✅ |
| 真实 XML：英文首页 | home（翻译路径）✅ |
| 真实 XML：相册 | album（原文路径）✅ |
| 空缓存 + 有模型 | 自动补表 10 条 → home ✅ |
| 表已有内容 | 不再调模型 ✅ |
| 没有模型 | 降级 unknown，不报错 ✅ |

### 装配方式（2026-11-01）

能力通过 `StepContext.pageIdentify` 下发，调用点不用改：

```ts
// RunOptions
pageIdentify: {
  align?: 静态表 | AlignCache,
  alignModel?: (prompt) => Promise<string>,
  vision?: (prompt, imageBase64) => Promise<string>,
}
```

`runs-api` 里从 `modelControl` 自动装配：
- `alignModel` → `modelControl.complete(prompt, { maxTokens: 320 })`
- `vision` → 仅当 provider 实现 `completeWithImage` 时才提供（探测型，缺了自动跳过）

`currentPage(ctx, pages)` 不传参时就用 `ctx.pageIdentify`；显式传参优先。

验证（假 ctx）：无 pageIdentify → 只有关键词；有 alignModel → 英文也判对；
有 vision 且 XML 几乎无文字 → 截图读字判对；显式传参优先。

## 九、关键词自动采集（方案 C，2026-11-01 已实现）

用户只需标注「我现在在哪个页面」，词由系统统计出来，不用手填。

```
同一页面抓 N 次（每次滚动半屏，让正文变化）
      ↓
稳定词：出现率 ≥80% 的 = 界面固定元素（正文是随机的，会被筛掉）
      ↓
跨页去重：在 ≥2 个页面出现的词全部丢弃（首页/市集/消息…）
      ↓
产出该页独有的 3–8 个词
```

### 过滤规则

| 规则 | 目的 |
|---|---|
| 长度 2–12 字 | 太短无意义，太长是正文 |
| 纯数字/时间（`20`、`16:30`） | 不是界面特征 |
| 出现率 <80% | 排除随机内容 |
| 跨 ≥2 页出现 | 排除泛词 |
| 每页最多 8 个 | 保持精简 |

### 代码

| 位置 | 内容 |
|---|---|
| `keyword-collect.ts` | `collectKeywords(samples)` 纯统计；`assessCollection()` 判断结果是否可信 |
| `flow-xhs-publish/collect.ts` | `collectPageKeywords(ctx, pageId)` 设备侧采样（滚动 + 抓取 + 统计） |

### 实测（真实 XML）

| 页面 | 采到的词 |
|---|---|
| home | 菜单、关注、发现、同城、搜索、首页、市集、发布 |
| album | 关闭、全部、视频、照片、草稿箱、实况图、全屏图 |

规则验证：
- 跨页去重：`首页` 同时出现在两页 → 被剔除；
- 正文过滤：三次内容不同 → 只留 `滤镜`/`贴纸`；
- 纯图页 → 0 词并警告「建议用 Activity 或视觉兜底」。

### 排查记录：页面表编辑原本不会落盘（已修）

自动保存只挂在画布的 `onContentChange` 上，而改全局变量类型（页面表就是这么存的）
**不会触发**它——所以关键词、标题、增删行在刷新后全部丢失。

更隐蔽的一点：`workflow.save()` 保存的是 **editor 里加载时的快照**（`doc`），
不是画布当前状态；内容"没变"会被幂等检查直接跳过，看着返回成功、实际没写盘。

修法：在 `commit` 之后按自动保存的同一形状自行保存——

```ts
const live = document.toJSON()
const schema = JsonSchemaUtils.astToSchema(globalVar.type)
await saveWorkflow(fileName, { ...live, globalVariable: schema })
```

防抖 800ms。实测：改关键词 → 5 秒后文件 mtime 更新、值正确。

### 排查记录：改了内核代码必须重新构建

内核跑的是各包的 `lib/index.js`（tsdown 产物），不是 `src/`。只跑 `tsc -b` 只更新类型，
路由不会生效（表现为新加的路由返回 401，被 `/api` 的准入层截住）。

正确流程：

```
npx tsc -b tsconfig.host.json   # 生成 lib/types
npx tsdown                     # 打包成 lib/index.js
```

顺带修了 `tsconfig.host.json` 里指向 `packages/app/kernel`（不存在）的悬空引用。

### 截图读字（L2）：已实现（2026-11-01）

XML 里几乎没有文字时（纯图片页），让视觉模型**读字**，再走同一套关键词匹配。

| 位置 | 内容 |
|---|---|
| `screen-ocr.ts` | `OCR_PROMPT`（完整列出/不要编号/不要求计数）、`parseOcrText`、`readScreenText` |
| `model-openai` | 新增 `completeWithImage()`（OpenAI 多模态 content 数组） |
| `currentPage` | 文字条数 < 3 且给了 `vision` 时触发；读到的字先原文匹配、再查对齐表 |

触发条件：`texts.filter(t => t.length >= 2).length < 3`——避免在文字充足的页面上浪费 5–7 秒。

实测（真实截图，缩放到 450px）：

| 截图 | 读字耗时 | 判定 |
|---|---|---|
| 图片编辑页 | 5.1s | image-editor ✅ |
| 相册页 | 6.0s | album ✅ |

解析细节：模型会加 `1.` `-` `•` `**` 等标记，`parseOcrText` 全部剥掉；
超过 40 字的行（帖子正文）直接丢弃。
## 十、判定打分与采集体验（2026-11-01 补齐）

### 加权打分（替换「数命中个数」）

| 规则 | 说明 |
|---|---|
| 权重 = 词长 | 词越长越具体（`一键成片` 4 分 vs `滤镜` 2 分） |
| 最低分 3 | 约等于「一个 3 字词」或「两个 2 字词」；单个 2 字词不算数 |
| 必须领先 | 与第二名同分即 unknown |

效果：`实况图`+`全屏图`（6 分）压过偶然命中的单个泛词；
只命中一个 `滤镜`（2 分）不会误判成图片编辑页。

### 采集体验

| 改进 | 行为 |
|---|---|
| 采集中状态 | 按钮显示「采集中」并禁用其他行按钮，防重复点击 |
| 覆盖前确认 | 该行已有关键词时弹窗对照「现有 / 新采」，取消则保留原值 |

实测：弹窗显示新旧对照、取消后原值保留 ✅；按钮文案 `采集 → 采集中` ✅。

### `video-editor` / `preview` 不填关键词

两者 Activity 名唯一（`VideoEditActivity` / `MaterialPreviewActivity`），
靠 Activity 就能可靠识别：

- `video-editor` 的界面词与图片编辑页高度重合（滤镜/贴纸…），硬填会互相抢分；
- `preview` 是纯图片页，抓不到文字，走截图读字或 Activity。

## 十一、属性匹配（2026-11-01 新增，通用）

关键词只能看「有哪些字」。XML 还有一批**与语言无关、与 App 无关**的属性可用。

### 真实数据（小红书首页，129 个节点）

| 属性 | 情况 | 可用性 |
|---|---|---|
| `text` / `content-desc` | 正常，但会被本地化 | ✅（值需过对齐表） |
| `class` | 14 种，多是 `TextView` / `FrameLayout` | ✅ **标准控件类名跨 App 通用** |
| `selected` / `checked` | 系统状态 | ✅ |
| `resource-id` | 小红书 79/129 个节点共用 `0_resource_name_obfuscated` | ⚠️ 该 App 不可用，别家 App 可能是稳定指纹 |
| `package` / `bounds` / `clickable` / `enabled` / `focused` / `scrollable` | 都有 | ✅ 可选 |

关键：选中项的类是 **`androidx.appcompat.app.ActionBar$Tab`**——Android 标准控件，
不是某个 App 私有，所以拿它当判据是通用的。

### 页面表怎么填

```json
{
  "id": "feed-explore",
  "attributes": [
    { "class": "~ActionBar$Tab", "selected": "true", "content-desc": "发现" }
  ]
}
```

| 写法 | 含义 |
|---|---|
| 一组内的多个键 | **AND**，必须同一个节点同时满足 |
| 数组里多组 | **OR**，任意一组命中即可 |
| 值以 `~` 开头 | 包含匹配（`class: "~ActionBar$Tab"`） |
| 否则 | 精确相等（`selected: "true"`） |
| 多页命中 | 取**条件字段最多**的（更具体优先） |

### 判定顺序

```
Activity.markers → attributes（属性）→ contentMarkers → 关键词 → 对齐表 → 截图读字 → 补表 → unknown
```

属性在关键词之前：更稳（系统状态）、更便宜（同一份快照）。

### 多语言

属性值同样会本地化（`content-desc="发现"` vs `"Explore"`），
所以属性匹配失败时会**用同一张对齐表翻译 `text` / `content-desc` 后再试一次**。

实测：
- 中文 XML → 原文即命中 `feed-explore`；
- 英文 XML → 原文 `unknown`，经对齐表（`Explore=发现`）后命中 ✅。

### 适用边界

- 属性匹配**不替代关键词**：两者是并列判据，业务按需选用；
- 混淆严重的 App（如小红书）别指望 `resource-id`，优先用 `class` + `selected` + 文案；
- 纯图片页仍然只有截图读字一条路。

## 十四、删掉「状态约束 / 控件类型」（2026-11-02）

### 结论：这两个字段是过度设计，已全部移除

它们是为「同一 App 内不同 tab 的文字完全相同」设计的：给关键词加
`keywordStates: ['selected']` 或 `widgetClass: 'Tab'`，才能区分「RED 出现在屏幕上」
和「当前就在 RED 页」。

删掉的原因（用户原话：「分 tab 跟关键词不可取，只能用关键词判断页面」）：

1. **与通用工具的定位冲突**：这本质是给某个 App 的 UI 结构做特例；
2. **大部分页面用不到**：12 个页面里只有首页可能需要，其余空着占地方；
3. **概念负担**：「状态约束」「控件类型」这两个词用户看不懂怎么填；
4. **真正的问题是页面定义错了**：如果同一 Activity 下两个 tab 文字完全相同，
   那它们就不是两个页面——不该用关键词区分。

### 一并删除

| 层 | 删除内容 |
|---|---|
| 引擎 | `PageSpec.keywordStates` / `widgetClass`、`KeywordState` / `KeywordNode` 类型、`resolveByKeywordNodes`、`hasKeywordStates` |
| `currentPage` | 节点级判定分支（回到纯文字匹配） |
| 前端 | 页面表里的两个下拉、采集时的自动建议 |
| 测试 | 「关键词 + 节点状态」「关键词 + 控件类型」两组用例 |

### 保留的

`PageSpec.attributes`（按 XML 属性匹配）**保留**——它是引擎级通用能力，
不绑某个 App，供将来需要时在 JSON 里直接用；界面上不暴露。

### 现在页面表就三行

```
[页面 id]  [中文名]        [删除]
[识别特征: Activity]
[界面关键词 .......] [采集]
```

实测：面板里「状态约束」「控件类型」均不再出现；12 个页面、10 个有关键词，功能正常。
