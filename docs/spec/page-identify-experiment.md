# 页面识别：本地模型可行性实测

日期：2026-11-01
设备：`127.0.0.1:5565`（Android 900×1600，小红书）
模型：`minicpm46`（1.64GB，视觉，项目默认定位模型）
脚本：`.tmp/page-identify-20261101_132519.mjs`、`.tmp/page-pair-20261101_133500.mjs`

---

## 一、要验证的方案

用户提出：**用本地模型判断「当前在哪个界面」**，链路是

```
用户提供页面特征（文字描述 或 图片）
  → 先拿 XML 里的文字比对
  → XML 比不出来，再用截图比对
```

实测分三段：L1 XML 文字比对、L2 截图闭集分类、L2' 参考图 1v1 比对。

## 二、结论

| 环节 | 可行性 | 实测 |
|---|---|---|
| **L1 文字描述 → XML 比对** | ✅ **可行，作主路径** | 当前首页命中 78%，第二名 17%，判定明确；耗时 2.3s（几乎全是 `uiautomator dump`） |
| **L2 截图 → 闭集分类（12 候选）** | ❌ **不可行** | 4 张样本只对 1 张（30% 缩放）/ 0 张（50% 缩放） |
| **L2 截图 → 闭集分类（预筛 3 候选）** | ❌ **不可行** | 2 张样本全错 |
| **L2' 参考图 1v1 比对** | ❌ **不可行** | 不同界面也答「是」（假阳性），单次 6.8–13.3s |

**一句话**：文字比对这条路成立；截图比对用 1.6B 的 minicpm46 判不出页面，别接。

## 三、L1 明细（真实设备，当前首页）

```
home            78%  命中 7/9  首页、市集、消息、关注、发现、同城、搜索
post-editor     17%  命中 1/6  发布
photo-picker    17%  命中 1/6  视频
→ 判定 home，耗时 2263ms
```

规则：命中率 ≥34% 且与第二名差距 ≥10% 才判；否则转下一层。

此时 XML 为空（如 `MaterialPreviewActivity` 那种纯 ImageView 页）→ L1 自然判不出，会落到 L2。

## 四、L2 明细（截图分类）

## 五、为什么不行（与既有结论一致）

`docs/spec/local-model-ui-locate.md` 已实测过：

- 整页截图 900×1600 → 2362 tokens，**38.8s**；裁剪后 5.3s，**视觉必须裁剪**。
- **「预筛比视觉有效 10 倍」**：全量 19 目标 + 截图 70%，纯文本 90%，预筛 5 目标 **100%**。
- 「加视觉反而降低准确率」——1.5B 模型有效注意力窗口很窄，候选越多、模态越多越差。

本次实测把这条推广到了**页面级分类**：12 候选 + 截图，1.6B 模型崩；缩到 3 个也不行（因为候选本身相似）。

顺带一条工程事实：**缩图对速度影响巨大**（100% 19.6s → 50% 6.9s → 30% 2.4s），如果将来确实要用视觉，必须缩图；但缩图会让界面文字不可读，与「靠文字区分页面」互相矛盾。

## 六、建议的做法

```
第 1 层  用户给的「界面上的字」→ XML 文字比对         2.3s   主路径，确定性
  ↓ XML 里没有可用文字（纯 ImageView 页）
第 2 层  确定性线索：Activity 名 / 页面表 markers       毫秒级
  ↓ 仍然认不出
第 3 层  报 unknown，交给流程的等待/重试与人工补规则
```

即：**页面识别继续走「文字 + Activity」这类确定性特征，不接小模型截图识别。**
真的需要视觉时，做法应是「参考图裁剪固定区域 → 纯代码像素/直方图相似度」（毫秒级），
或者换 35B-A3B 这类大模型（实测 100%，3.3s，19.89GB，需 llama.cpp `-nr`），而不是 1.6B。

## 七、踩坑记录

| 项 | 说明 |
|---|---|
| **样本文件名不可信** | `data/anom_home.png` 实际是**个人主页**，不是首页；判定前必须看图确认 ground truth |
| `uiautomator dump` 退出码 139 | 本机设备上文件已写好但进程返回 139，脚本不能因退出码中断 |
| 模型不回「编号」 | 让它「只输出编号」，minicpm46 仍会输出 `1. home：首页信息流…`，解析要容错 |

# 补充：35B-A3B 实测（2026-11-01）

## 前提：ollama 里的 m35 是「纯文本封装」，但模型本身有视觉

`ollama /api/show m35` 返回 `capabilities: ['tools','thinking','completion']`——没有 vision。
原因是那个模型是用 `FROM <主 gguf>` 直接建的（见它的 Modelfile），**没挂投影层**。

模型本身是 MiniCPM-V 4.7 35B-A3B（GGUF `general.name = 35a3_hf_v47_0923`），
视觉投影层单独存在磁盘上：

```
F:/ai/deepseek/blobs/sha256-1e0ab439877e6…   0.90GB
  general.name       = Hf_V47_4X
  clip.projector_type = minicpmv4_7
  clip.vision.image_size = 448, patch = 14
```

用 llama.cpp 起服务时加 `--mmproj` 指过去就能看图，ollama 那份封装做不到。

**但本机这份 llama.cpp 挂不上它**（2026-11-01 实测）：

```
llama-server -m <19.89GB> --mmproj <0.90GB clip> -c 4096 -nr -t 8 -ngl 0
→ clip_init: failed to load model '...sha256-1e0ab439877e6'
  clip_model_loader: failed to load CLIP model
```

原因不是文件坏，是**版本不支持**该投影层类型：

```
mtmd.dll 内含:  minicpmv4_6  ✅
mtmd.dll 不含:  minicpmv4_7  ❌   ← 这个投影层要的就是它
llama.cpp 版本: 0.8.0-dev (build 11985, commit 6d194531e)
```

盘上只有一个 llama.cpp（`F:/ai/tools/llamacpp`，b11985）。另外下载了最新 nightly
`b12024` 验证：**它的 `mtmd.dll` 同样只有 `minicpmv4_6`，没有 `minicpmv4_7`**。
即**主线 llama.cpp 目前还不支持这个投影层**（已删除该临时下载）。

### 换 ollama 这条路：认得出模型，但内存装不下

ollama 的 `lib/ollama/libmtmd.dll` 里**有** `minicpmv4_7`（9 处），它支持这个投影层。
做法：复制一份 manifest 并补上 projector 层（零拷贝，不改原 `m35`）：

```
manifests-v2/ollama.com/library/m35vl/latest
  layers += application/vnd.ollama.image.projector
            sha256:1e0ab4398…
```

另起一个实例（不动你正在跑的那个）：

```
OLLAMA_HOST=127.0.0.1:11435  LLAMA_ARG_REPACK=0  ollama serve
```

结果：`/api/show m35vl` → `capabilities` 含 **vision** ✅，但推理时加载失败：

```
load_tensors: loading model tensors ... (load_mode = none)
ggml_backend_cpu_buffer_type_alloc_buffer: failed to allocate buffer of size 19878416128
error loading model: unable to allocate CPU buffer
```

两处关键：

| 现象 | 说明 |
|---|---|
| `LLAMA_ARG_REPACK=0` 有效 | 不再要 18.1GB 的 `CPU_REPACK` 缓冲（这就是 `-nr` 的作用，实测坐实） |
| `load_mode = none` | ollama 把这个模型**整块装进内存**（不走 mmap），需要 **19.88GB 连续内存** |

**为什么 ollama 不走 mmap**——它日志里写得很直接：

```
disabling mmap for llama-server load by default   reason=cpu
"starting llama-server" cmd="... --load-mode none ..."
warn: LLAMA_ARG_LOAD_MODE is set, but will be overwritten by command line argument --load-mode
```

即：**纯 CPU 模式下 ollama 主动关掉 mmap**，并且用命令行参数覆盖了环境变量，
`LLAMA_ARG_LOAD_MODE` 改不动它。

> 注：19.89GB 的 MoE 模型**本来就不需要 20GB 内存**——llama.cpp 用 mmap 时
> 实测只驻留 **1.47GB**（见上一节的文本测试）。所以「3GB 就能跑」是对的，
> 限制来自 ollama 的加载策略，不是模型本身。

### 35B 视觉的现状

| 路径 | 结果 |
|---|---|
| llama.cpp（b11985 / b12024） | ❌ 不支持 `minicpmv4_7`，CLIP 加载失败 |
| ollama（`m35vl`，REPACK=0） | ❌ 支持投影层，但 CPU 模式强制关 mmap → 要 19.88GB 连续内存 |
| **ollama 自带的 `lib/ollama/llama-server.exe`** | ✅ 能绕开加载策略：我们直接调它并传 `--load-mode mmap -nr`，**内存问题消失**，进入下一阶段 |
| 但本机 `minicpmv4_7` 投影层只有 **dim=1024（1B 版）** | ❌ 与 35B 的 `n_embd=2048` 不匹配：`mismatch between text model (n_embd = 2048) and mmproj (n_embd = 1024)` |

### 关键结论：不是内存问题

- 19.89GB 的 MoE 用 **mmap** 只需 **1.47GB** 驻留（文本测试实测），"3GB 就能跑"成立；
- ollama 之所以要 19.88GB，是它 **CPU 模式主动禁用 mmap**（日志 `disabling mmap ... reason=cpu`，
  并强行传 `--load-mode none`，环境变量无效）；
- 改用 **ollama 自带的 llama-server + `--load-mode mmap`** 后，内存不再是障碍。

### 真正的缺口：35B 的视觉投影层不在本机

本机仅有的 `minicpmv4_7` 投影层是 **1B 版**（0.90GB，dim=1024）。
35B 需要 `openbmb/MiniCPM-V-4.7-35B-A3B-gguf` 仓库里的 **`mmproj-model-f16-4x.gguf`（910MB）**。
`.tmp/mmproj-model-f16.gguf.parts/` 是此前**没下完**的分块目录，不可用。

顺带验证：用配套的 1B（0.67GB）+ 它的投影层能正常加载并看图，
但 1B 的答题质量差（14.5s/次，输出混乱、会列多个候选），不适合做页面判定。

### 35B 视觉：加载成功 ✅

从 `openbmb/MiniCPM-V-4.7-35B-A3B-gguf` 下载 `mmproj-model-f16-4x.gguf`（868MiB）后：

```
general.name            = Hf_35B_4X
clip.vision.projection_dim = 2048      ← 与 35B 的 n_embd=2048 匹配
clip.projector_type     = minicpmv4_7
```

用 ollama 自带的 llama-server + mmap 启动：

```
llama-server -m <19.89GB gguf> --mmproj mmproj-f16-4x.gguf \
             --load-mode mmap -nr -t 8 -ngl 0 -c 4096
→ load_model: loaded multimodal model ✅
→ listening on http://127.0.0.1:8096     （4.1 秒完成加载，无内存报错）
```

**结论：35B-A3B 的视觉在本机跑得起来，前提是**
1. 必须用 `--load-mode mmap`（ollama 默认关掉，才会要 20GB）；
2. 必须挂与 `n_embd` 匹配的投影层（35B 用 `dim=2048` 的 `Hf_35B_4X`，不是 1B 那个 `dim=1024`）。

### 实测：判对了，但 3 分钟一次

输入：`data/anom_album.png`（相册页，缩到 50%）+ 12 个候选页面描述。

| 模型/模式 | 输出 | 判定 | 耗时 | 内存 |
|---|---|---|---|---|
| **35B 视觉**（mmap + Hf_35B_4X） | `9` | **album ✅** | **186,465ms** | 私有 **2.15GB**，工作集 13.9GB（文件映射，可回收） |
| 1B 视觉（minicpm47 1B） | 混乱，列多个候选 | ❌ | 14,529ms | — |
| 35B 文本（`-nr`） | `11` | home ✅ | 59,516ms | 工作集 1.47GB |
| minicpm46 文本 | `1. home` | home ✅ | 173ms | — |

**"3GB 就能跑"得到证实**：私有内存仅 2.15GB，其余是 mmap 的文件页（可回收）。
运行期间系统显示"可用 0.3GB"是文件缓存被占满的假象，不是真实需求。

**但 186 秒/次**：CPU + 换页，放进「每步判页面」的循环里不可用。
文档早先记的 3.3s 应是文本模式且文件已在系统缓存里，不是视觉。

### 调优后：14 秒/次（提速 13 倍）

耗时**全部在 prompt 处理**（生成为 0.2s），所以优化方向是"少 token + 高吞吐"：

| 配置 | 耗时 | 判定 |
|---|---|---|
| `-t 8`、默认 ubatch、`-c 4096`、12 候选、图 50% | 186s | ✅ |
| `-t 12 -ub 1024 -fa on -c 2048`、12 候选、图 50% | 88s | ✅ |
| **+ 候选预筛到 3 个 + 图 30%** | **18.3s → 稳态 14.2s** | ✅ |
| 同一张图重复（prompt 缓存命中） | **0.6s** | ✅ |

三条有效手段：

1. **候选预筛**：先 XML 文字缩小到 ≤3 个页面，候选文本 350 → 100 token；
2. **图片 30%**：模型会把图归一化到固定网格（实测 30% 与 20% 的 token 数相同，都是 378），
   50% 纯属浪费；
3. **线程拉满**：6 物理/12 逻辑核，`-t 12` 比 `-t 8` 快一倍。

推荐参数：

```
--load-mode mmap -nr -t 12 -ngl 0 -c 2048 -b 2048 -ub 1024 -fa on
```

### 换小模型：MiniCPM-V 4.6 → 2.5 秒，更实用

35B 的 14 秒受限于 CPU 内存带宽（暖机后也只有 27–29 tok/s），再调参数无空间。
改用 **MiniCPM-V 4.6**（模型 0.53GB + 投影层 1.11GB），同样参数、同样 3 候选、图 30%：

| 样本 | 期望 | 4.6 判定 | 耗时 |
|---|---|---|---|
| `anom_album.png` | album | album ✅ | 2432ms |
| `anom_home.png` | profile | profile ✅ | 2553ms |
| 真机截图（当前首页） | home | home ✅ | 2502ms |

**3/3 正确、约 2.5 秒**（35B 是 14.2 秒，快 5.6 倍）。

对照三个视觉模型（同参数、3 候选）：

| 模型 | 体积 | 准确 | 耗时 |
|---|---|---|---|
| MiniCPM-V 4.6 | 0.53+1.11GB | 3/3 | **2.5s** |
| MiniCPM-V 4.7 1B | 0.67+0.90GB | 1/2（把个人主页判成相册） | 5.2s |
| MiniCPM-V 4.7 35B-A3B | 19.89+0.87GB | 2/2 | 14.2s |

**预筛是硬前提**：同一张图给 12 个候选，4.6 输出 `1.0`（误判 permission）；
给 3 个候选才 2.5 秒且正确。

### 但 4.6 只在「页面差别大」时可用

补测两张**相似页面**（先看图确认 ground truth）：

| 样本 | 实际页面 | 4.6 判定 | 35B 判定 |
|---|---|---|---|
| `anom_editor.png` | image-editor（滤镜/贴纸/下一步） | preview ❌ | **image-editor ✅**（37.0s） |
| `anom_preview.png` | review（整图 + 一键成片/下一步/选择） | preview ❌ | **review ✅**（26.3s） |

汇总：

| 样本组 | 4.6 | 35B |
|---|---|---|
| 易区分（album / profile / home） | 3/3 ✅（2.5s） | 2/2 ✅（14s） |
| **难区分（image-editor / review / preview）** | **0/2 ❌** | **2/2 ✅**（26–37s） |

**结论：不是"小模型够用"，而是"小模型只能分辨长得不一样的页面"。**
`image-editor` / `review` / `preview` 三者都是"一张大图 + 底部按钮"，4.6 直接混成一个。

### 最终可用性判断

| 路径 | 耗时 | 适用 |
|---|---|---|
| XML 文字比对 | 2.3s | **主路径**，确定性 |
| Activity（`markers`） | 毫秒 | 与 XML 互补 |
| 4.6 视觉 | 2.5s | 仅当候选**外观差异明显** |
| 35B 视觉 | 14–37s | 仅当候选**外观相似**且值得等 |
| 纯文本模型 | 0.17s | 有文字时永远优先 |

**建议**：视觉兜底做成"可选 + 有超时 + 失败就 unknown"，不要当作可靠的最后一环。
| 对照：llama.cpp 纯文本（`-nr`） | ✅ 能跑，但慢（换页，1.95 tok/s） |

要真正跑通 35B 视觉，二选一：
1. **腾出 ≥20GB 空闲内存**（关掉大应用或重启后立刻测），用 ollama 的 `m35vl`；
2. **等 llama.cpp 主线支持 `minicpmv4_7`**（当前最新 nightly 也不支持）。

补充：测试时在模型库里新增了 `m35vl` 条目（只加了一个 manifest 文件，未复制权重）。
不需要时删掉 `F:/ai/deepseek/manifests-v2/ollama.com/library/m35vl/` 即可。

## 启动方式

`-nr` = `--no-repack`（关掉量化权重重排），本机 llama.cpp 0.8.0-dev (build 11985) 支持。

## 结果：判对了，但慢 340 倍

同一份输入：当前设备界面 28 条文字 + 12 个候选页面描述，只输出一个。

| 模型 | 输出 | 判定 | 耗时 |
|---|---|---|---|
| **35B-A3B**（llama.cpp，CPU） | `11` | home ✅ | **59,516ms** |
| **minicpm46**（ollama，文本） | `1. home` | home ✅ | **173ms**（热） |

**准确率没有差别，速度差 344 倍。**

## 为什么 59 秒：内存装不下

服务端日志：

```
prompt eval time = 58403 ms / 463 tokens (7.93 tokens/s)
eval time        =  1023 ms /   3 tokens (1.95 tokens/s)
```

而运行时实测：

| 指标 | 数值 |
|---|---|
| 系统可用内存 | **0.4GB** |
| 模型工作集 | **1.47GB**（远小于 19.89GB） |

即模型基本没驻留内存，**每个 token 都在从磁盘换页**。
关掉服务后可用内存回到 13.2GB —— 仍小于模型体积的 19.89GB。

**这台机器（27.9GB 总内存）在开着开发环境时跑不动 19.89GB 的 35B。**
早先记录的 3.3s 需要约 20GB 空闲内存，现在不成立。

## 结论

1. **35B-A3B 判页面是准的**，但本机当前配置下 59s/次，放进「每步都判页面」的循环里不可用。
2. **它没有比 minicpm46（173ms）更准**，更没有比纯代码的关键词比对（2.3s，几乎全是 dump 耗时）更准。
3. 想让它快，前提是给够内存（≥20GB 空闲）或上 GPU；本机现状不满足。
4. 因此维持原建议：**页面识别走文字特征比对 + Activity，不接视觉/大模型**。

## 踩坑

| 项 | 说明 |
|---|---|
| **输出格式不守约** | 让它「只输出编号」，minicpm46 回 `1. home`（给成了 id）；解析必须先认 id 再认编号，否则误判 |
| **进程残留** | 前面服务启动失败过几次，实际留下了两个 llama-server，白占内存；起之前先查同名进程 |

# 补充：视觉模型到底"看得见"什么（2026-11-01 探测）

用「完整列出截图上的所有文字」直接问 MiniCPM-V 4.6，看它的识读能力。

## 结论

| 内容类型 | 30% 缩放（270px） | 50% 缩放（450px） |
|---|---|---|
| 大号字（底部导航、顶部 tab） | ✅ 准：关注 / 发现 / 同城 / 市集 / 我 | ✅ |
| 中等字（工具栏标签） | ❌ 糊成「交 稿 制 记 访 购 息」 | ✅ 准：滤镜 / 文字 / 贴纸 / 切割 / 标记 / 调节 / 拼图 |
| 页面标题（如「选择音乐」「下一步」） | ⚠️ 部分错：读成「选择背景」「音乐 选系务」 | ✅ 准 |
| 小字 / 正文 | ❌ 错字、臆造 | ⚠️ 仍会错（一键成片 → 一步成片；草稿箱 → 算辑箱） |
| 布局类型 | ✅ 能判断（"整屏大图"vs"网格"），这正是它把相似页混为一谈的原因 |

耗时（4.6，12 线程）：30% 约 2.6–5.7s；50% 约 2–7s（视文字量）。

## 用法启示

1. **不要让它"选页面"**，让它**读字**，再用与 XML 同一套关键词匹配 → 把不稳定的分类变成确定性匹配。
2. 关键词要**容错**：`一键成片` 可能读成 `一步成片`/`一帧成片`，应匹配 `成片`；
   `草稿箱` 可能读成 `算辑箱`；`裁切` 可能读成 `切割`。
3. 需要读工具栏/小字时，图不能小于 **50%**（30% 直接不可用）。
4. 正文会混进大量噪声（信息流文案），匹配时应只看**短词、高频 UI 词**，忽略长句。

# 补充：像人一样的判断模式（读字 → 判断）

## 分辨率对照（MiniCPM-V 4.6，读图上的字）

| 缩放 | 耗时 | 能读到什么 |
|---|---|---|
| 30%（270px） | 2.6–5.7s | 只有大号字（关注/发现/同城/市集/我） |
| **50%（450px）** | **约 7s** | 工具栏可读（滤镜/文字/贴纸/切割/标记/调节/拼图），个别错字（裁切→切割） |
| 75%（675px） | 14.7s | **全部正确**（含 裁切、图文） |
| 100%（900px） | 18.8s | 同上，额外读到水印「豆包AI生成」 |

结论：**50% 是性价比拐点，75% 是需要精确小字时的选择**；100% 无额外收益。

## 模式：OCR → 文本判断（两段式）

```
L1  视觉模型读字：截图 → 「完整列出所有文字」
L2  文本模型判断：读到的文字 + 候选页面描述 → 页面 id（0.5–1.2s）
```

和「直接让视觉模型选页面」对比（同样 3 个候选、同样 50%）：

| 页面 | 直接选页面 | 读字 → 判断 |
|---|---|---|
| 图片编辑页 | ❌ preview | ✅ image-editor |
| 图片预览页 | ❌ preview | ✅ review |
| 相册页 | — | ✅ album |

**读字方案把三个难例全判对**，直接选页面在相似页上全错。

### 两个关键前提

1. **候选描述要容错**：写 `成片` 而不是 `一键成片`（OCR 会读成「一步成片」）；
   写 `裁切/切割` 两种写法。
2. **判断提示词要声明 OCR 可能错字**：「文字是 OCR 结果，可能有错字（如草稿箱→算辑箱），按意思最接近的判断」。
   加这一句后，相册页从误判 profile 变为正确 album。

### L2 其实可以先不调模型

把上面三段**真实 OCR 结果**直接喂给纯关键词匹配（容错写法），结果：

```
图片编辑页  期望=image-editor  判定=image-editor  ✅  命中: 滤镜/贴纸/拼图/标记/调节/文字
图片预览页  期望=review        判定=review        ✅  命中: 成片/下一步
相册页      期望=album         判定=album         ✅  命中: 全部/视频/照片/实况图/全屏图/辑箱
纯关键词：3/3
```

所以 L2 分两档：
1. **关键词匹配**（0 成本、确定性）——先走这个；
2. 匹配不出或有歧义 → 才用**文本模型**判断（0.5–1.2s）。

### 成本

| 阶段 | 未缓存 | 已缓存 |
|---|---|---|
| L1 读字（50%） | 约 7s | 1–3s |
| L2 关键词匹配 | **0ms** | 0ms |
| L2' 文本模型（仅兜底） | 0.5–1.2s | — |
| **合计** | **约 7s** | 1–3s |

对比：直接选页面 2.5s（但相似页会错）；XML 文字匹配 2.3s（确定性，最优先）。

# 补充：35B-A3B 对「同布局不同内容」的判断（2026-11-01）

送两张**界面框架完全相同、只有 feed 内容不同**的首页截图，问三个问题，耗时 **126.9 秒**：

> 1. 页面结构（顶部导航、底部导航、整体布局）相同。
> 2. 内容不同。
> 3. 它们是同一个页面类型（均为"发现"页的信息流界面）。

**答案完全正确**，而且它把"结构相同 / 内容不同 / 页面类型相同"拆开回答了——
说明 **35B-A3B 的判断力够用，瓶颈只在速度**（单图 14–37s、双图 127s）。

对比 4.6：2.5 秒，但对相似页会把 `image-editor` / `review` / `preview` 混为一谈。

| 模型 | 判断力 | 速度 | 用途 |
|---|---|---|---|
| 4.6 | 弱（只看得出布局差异大的） | 2.5s | 运行时兜底 |
| 35B-A3B | **强**（能区分结构与内容） | 14–127s | 离线核对 / 难题复核 |

也印证了：**同布局、只有内容不同的两张图，不应该判成两个页面**；
真要区分（不同 tab），只能靠 XML 的 `selected` 属性或 Activity，视觉模型无能为力。
