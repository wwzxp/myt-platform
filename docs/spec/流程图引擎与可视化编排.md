# 流程图引擎与可视化编排（Spec）

> 状态：图引擎 + 三个流程迁移完成（22 个单元测试 + 三流程真机跑通），待做画布 UI
> 关联：[CONTEXT.md](../../CONTEXT.md)（术语）、[ADR-0001](../adr/ADR-0001-architecture-baseline.md)（架构基线）

## Problem Statement

现在的流程是**平铺的动作数组**，三分支逻辑全部隐藏在代码里，用户在 UI 上看不到、也改不了：

| 隐藏在代码里的行为 | 位置 | 用户看到什么 |
|---|---|---|
| 没有标题就跳过 | `if (!input.title) return` | 什么都看不到 |
| 没有图片就跳过 | `if (input.imagePaths.length === 0) return` | 什么都看不到 |
| 不是音乐图集就跳过 | `if (!input.musicImg) return` | 什么都看不到 |
| 找不到元素就跳过（`optional`） | 引擎内置 | 一个布尔开关 |
| 页面不对就恢复（`recoverable`） | 引擎内置 | 一个布尔开关 |
| 失败就整单停 | `if (!result.ok) throw` | 看不到 |

**后果**：

1. 改流程必须改代码、重新构建、重新跑真机验证（一轮 90 秒）。
2. 业务人员无法自己调整流程顺序或分支。
3. 出了问题是哪一步、走了哪条路，只能翻日志。
4. 加新 App（抖音、快手）必须写代码。

## Solution

把流程从「平铺数组」改成**有向图**，并在 UI 上以画布形式可视化编辑：

- 每个**动作节点**都有独立端口：`success` / `failure` / `mismatch`（页面不对）
- **条件节点**（`true` / `false`）和**循环节点**（`body` / `done`）承担原本隐藏在代码里的分支
- 流程定义存成 **JSON 文件**（`data/flows/*.json`），运行时加载，改流程不用改代码
- 画布直接读写这些 JSON，节点配置通过属性面板可视化编辑
- **现有 UI 整体重做**，用 `design-taste` 技能的 app screen 规范重新设计

## 界面文案规范

UI 最终给业务人员看，**不用专业术语当标签**。分三层：

| 层 | 语言 | 例子 |
|---|---|---|
| **界面标签、节点名** | 中文大众词 | 「填写标题」而不是 `fill-title`；「打开笔记页」而不是 `open-post-editor` |
| **悬浮释义** | 中文解释专业概念 | 鼠标悬浮「恢复规则」→「页面不对时自动做什么」 |
| **代码标识符** | 英文 | `FlowGraph`、`actionNode`、`portId`（与 STYLE.md §3 一致） |

**释义放在哪**：每个专业词在界面上都有 `title` 属性（浏览器原生悬浮提示）或自绘 tooltip，内容是一句话中文解释 + 一个例子。不需要用户先学概念。

**已知需要释义的词**：

| 界面用词 | 释义 |
|---|---|
| 动作 | 在手机上做一件事：点一下、输文字、滑一下 |
| 端口 | 这一步走完后，下一条路往哪走 |
| 成功 / 失败 / 页面不对 | 三种结果，分别连到不同的下一步 |
| 条件 | 先判断一下，再决定走哪条路 |
| 循环 | 重复做几次 |
| 定位 | 怎么在屏幕上找到要点的东西 |
| 兜底 | 自动找失败时，用预先写死的位置再试一次 |
| 恢复 | 页面跑到别处了，怎么退回来 |
| 页面表 | 这个 App 有哪些界面，各自怎么认出来 |
| 轮数 | 最多试几次 |
| 间隔 | 每次之间等多久 |

> **实施状态（2026-11-01）**：界面标签已全量中文化——节点面板用 `info.title`（缺省回落类型名），
> 每个节点项把 `info.description` 作为 `title` 悬浮释义；试运行面板、节点菜单、缩放、状态栏、
> 快捷键名、HTTP 体类型等英文串均已替换。
>
> i18n 语言固定为 `zh-CN`（原先取 `navigator.language`，英文系统会把 flowgram 自带文案渲染成英文），
> 并补齐 flowgram 的 24 个文案键。逐按钮实测（悬停读 Tooltip、逐面板扫描 DOM 文本）：
> 工具栏 12 个图标按钮 + 添加节点 + 试运行、节点右键菜单 3 项、节点面板 9 项、
> 缩放菜单 6 项、变量面板 2 个页签、试运行面板、问题面板 —— 均无英文残留。
>
> **按规范保留英文**：`JSON`/`GET`/`PNG` 等协议与格式名（第三层），
> `app`/`maxSteps` 等变量名，以及 `<code>data/workflows/</code>` 这类路径。
>
> **未覆盖**：端口名 `success` / `failure` / `mismatch` 由 flowgram 直接渲染 `portID`，
> 目前没有提供端口显示名的钩子；改成中文就得改引擎侧的端口标识，暂不动。

## User Stories

### 引擎与数据

1. 作为流程作者，我想把流程定义成 JSON 文件，这样改流程不用重新编译。
2. 作为流程作者，我想让每个动作都有 `success` / `failure` / `mismatch` 三个出口，这样失败后走哪条路是我决定的，不是引擎决定的。
3. 作为流程作者，我想用条件节点表达「有标题才填标题」，这样这个判断在画布上看得见。
4. 作为流程作者，我想用循环节点表达「最多重试 6 轮」，这样重试次数和循环体都可以在画布上看到。
5. 作为流程作者，我想让 JSON 在加载时被校验（缺字段、连到不存在的节点、有环），这样错误在启动时暴露，而不是跑到一半才崩。
6. 作为流程作者，我想让图有明确的入口和出口，这样执行路径唯一确定。

10. 作为运维人员，我想让每个节点的执行耗时和结果写入事件流，这样能看瓶颈在哪。

18. 作为流程作者，我想让画布自动布局，这样打开就能看清结构。
19. 作为流程作者，我想在动作节点里选「怎么找目标」——描述意图 / 比例坐标 / 绝对坐标，这样 UI 树看不到的元素（Canvas、WebView、游戏画面）也能操作。

### 界面文案

## Implementation Decisions

### 流程输入参数必须声明在「开始」节点

节点里引用的 `{{title}}` / `flowParams.imagePaths` 都是**流程输入参数**，它们必须由
「开始」节点的 `outputs`（JSON Schema）声明，否则：

- 「试运行」面板是空的，用户没地方填；
- 条件节点只能靠手敲 `imagePaths` 这种键名，没人看得懂。

```json
"outputs": {
  "type": "object",
  "properties": {
    "title":      { "type": "string", "title": "标题" },
    "imagePaths": { "type": "string", "title": "图片路径",
                    "description": "本地图片，多张用逗号分隔；不填就是纯文字" }
  },
  "required": ["title"]
}
```

三处据此统一：

| 位置 | 显示 |
|---|---|
| 试运行面板 | 用 `title` 当字段名（「图片路径」），不用键名；值由用户粘贴 |
| 条件节点 | 「看哪个输入」显示中文名 + 说明（只读），不再把键名摆给用户 |
| 未声明的键 | 条件节点上给出黄色提示「没有在「开始」里声明，运行时可能取不到值」 |

参数值本身**不由条件节点持有**：条件节点只判断「这个输入有没有值」。

**例外：图片路径不再走流程输入。** 用户反馈「为什么要去别处填、imagePaths 谁看得懂」，
所以图文流程改成：

- 删掉「有图片吗」条件分支（它对业务用户不可读，且 `imagePaths` 无从声明）；
- 「推送到相册」节点自带「图片路径」字段，用户直接粘路径（多张用逗号/换行）；
- 该动作会把路径同步写回 `flowParams.imagePaths`，后面的「选择图片」照旧按数量选图。

于是 `imagePaths` 从「开始」的参数里移除，其余（标题/正文/保存方式/音乐图集）仍在。

### 页面表：「页面是」能填什么

条件节点里的 `home` / `profile` 不是随便起的名字，而是**页面表**里的 id：

```json
// globalVariable.app.pages
{ "id": "home",    "title": "首页",   "markers": ["IndexActivity"] }
{ "id": "profile", "title": "个人页", "markers": ["ProfileActivity", "UserProfileActivity"] }
```

- `markers` 是**识别特征**：命中 Activity 名（或界面文字，见 `contentMarkers`）就判为该页。
- 节点上「页面 id」填 id，多个用英文逗号分隔（`home,profile` = 任一命中即成立）。
- 表单下方会列出**全部可填值**（中文名 + id），不用猜。

**遇到新界面怎么办**：在**「变量面板 → 页面表」**里加一行（页面 id + 中文名 + 识别特征），
条件节点的下拉里就会多出这个选项。登记需要知道该界面的 Activity 名——
`adb shell dumpsys window | grep mCurrentFocus` 可以拿到（或看 `uiautomator dump` 里的特征文字）。

- 「页面」字段是**多选下拉**，选项来自页面表，显示「首页（home）」这种中文名 + id。
- 页面清单与「新界面怎么加」的说明放在标签的悬浮提示里，不占表单空间。



图是「节点 + 连线」的有向图，节点带画布坐标（供 UI 渲染）。

```ts
interface FlowGraph {
  id: string
  title: string
  nodes: FlowNode[]
  edges: FlowEdge[]
  /** 业务配置（画布 JSON 的 `data` 扩展位）。 */
  data: {
    /** 目标 App 配置：包名、首页深链、页面表、恢复规则。 */
    app: AppConfig
    /** 最大执行步数，防止环形连线跑死。 */
    maxSteps: number
  }
  /** 入口节点 id；省略时自动取唯一的 start 节点。 */
  entry?: string
}

interface FlowNode {
  id: string
  /** 节点类型（与画布 `node.type` 完全一致）。 */
  type: NodeType
  /** 画布元信息。 */
  meta: { position: { x: number; y: number } }
  /** 业务数据；形状见「节点数据形状」一节。 */
  data: NodeData
  /** 循环容器的子节点。 */
  blocks?: FlowNode[]
}

/**
 * 可执行节点类型。
 *
 * 与画布 `WorkflowNodeType` 一一对应：画布能拖的，引擎必须能跑。
 * `group` / `comment` 不在此列——它们是纯视觉节点，不进图。
 */
type NodeType =
  | 'start'
  | 'mt-action'
  | 'mt-condition'
  | 'mt-loop'
  | 'condition'
  | 'loop'
  | 'http'
  | 'code'
  | 'llm'
  | 'variable'
  | 'end'

interface FlowEdge {
  sourceNodeID: string
  sourcePortID: PortId
  targetNodeID: string
}

type PortId = 'out' | 'success' | 'failure' | 'mismatch' | 'true' | 'false' | 'body' | 'done'
```

### 设备类动作与条件（2026-11-01）

产品面向非开发者：**节点上不出现代码标识，也不出现命令行**。通用操作用「做什么」下拉里的
**通用动词 + 可填参数**表达：

| 做什么 | 字段 | 引擎做的事 |
|---|---|---|
| 推送文件 | 本地路径、放到哪个目录（默认 `/data/local/tmp/`） | `adb push <本地> <目录>/<文件名>`，随后 `chmod 755` |
| 安装应用 | 安装包（本地 APK）、应用名（仅作标题/提示） | push 到临时目录 → `pm install -r -t` |
| 启用输入法 | 输入法（填名称的一部分，如 `adbkeyboard`） | `ime enable` → `ime set` |

- **文件名自动沿用**，用户不需要给手机上起名。推送后自动加执行权限（755）——`adb push`
  默认给 644，临时目录里的工具（如 yadb）不加就执行不了。
- **内置文件不暴露占位符**：模板里存的就是给人看的文字——`内置 ADB 输入法` / `内置 yadb`，
  引擎执行前翻译成真实路径（`MYT_ADB_KEYBOARD_APK` / `ctx.yadbPath`）。
  用户直接改这段文字就能换成自己的路径；旧模板里的 `{{adbKeyboardApk}}` 仍然兼容。
  没有「选择…」按钮——字段本身就是普通可编辑输入框。
- **输入法按名称片段匹配**：设备拿不到可读显示名（`ime list -a` 的 `nonLocalizedLabel` 为 `null`，
  只有资源 id），所以引擎把用户填的值当成片段，去 **`ime list -a`** 的结果里找
  （只解析「以 `:` 结尾」的 id 行，避免把 `sourceDir=/data/…` 当 id）：
  命中一个就切过去；命中多个报错并列出候选；一个都没有则报错并列出可用输入法。
  含 `/` 的值按完整标识直接使用。
  **必须用 `-a` 而不是 `-s`**：`-s` 只列已启用的，刚装上还没启用的输入法不在里面，
  会让「安装应用 → 启用输入法」这条链误判为「没有匹配的输入法」。

**高级场景**仍保留通用原语，但不在默认链路里：

| 原语 | 键 | 说明 |
|---|---|---|
| 动作 `adb` | `actKind='adb'`，参数 `actArgs` | 原样执行 `adb -s <serial> <args…>`；参数支持引号分组。**不做白名单** |
| 条件 `apkInstalled` | `judgeKind`，参数 `judgePackage` | `pm list packages <名字>` 输出里包含即成立 |
| 条件 `fileExists` | `judgeKind`，参数 `judgePath` | `ls <路径>` 不报错即成立 |

#### prepareEnvironment 的拆解结果

`prepareEnvironment` 已从「一个黑盒动作」拆成 **7 个可见节点**，全部是通用动作或可读条件：

```
已装 ADBKeyboard 吗 ─┬─ 是 ─────────────────────────┐
                     └─ 否 → 安装应用 ───────────────┴→ 启用输入法
                                                            ↓
设备上有 yadb 吗 ─┬─ 是 ───────────────────────────────┐
                  └─ 否 → 推送文件 ────────────────────┴→ 已经在首页或个人页吗
                                                              ├─ 是 → 下游
                                                              └─ 否 → 打开首页 → 下游
```

`prepareEnvironment` 这个一步到位的快捷动作**仍保留在注册表里**，需要时可直接用。

**与拆分前的行为差异**（有意为之，需知悉）：

| 维度 | 拆分前（`ensureIme`） | 拆分后（画布节点） |
|---|---|---|
| 失败处理 | `.catch(() => undefined)`，输入法失败**被吞掉**，流程继续 | 失败走 `failure` → `end`，**快速失败** |
| root 兜底 | `ime set` 失败时用 root 临时 disable/enable 当前输入法 | **没有**，直接失败 |

### 端口契约

| 节点类型 | 入口 | 出口 | 语义 |
|---|---|---|---|
| `start` | — | `out` | 流程入口，只能有一个 |
| `mt-action` | `in` | `success` / `failure` / `mismatch` | success = 动作成功；failure = 定位失败或校验不过；mismatch = 前置页面不符 |
| `mt-condition` | `in` | `true` / `false` | 条件成立走 true |
| `mt-loop` | `in` | `body` / `done` | 容器式循环，循环体在 `blocks` 里；未达次数走 body，达次数走 done |
| `condition` | `in` | `true` / `false` | demo 条件节点，纯变量比较 |
| `loop` | `in` | `body` / `done` | demo 循环节点，数组遍历 |
| `http` / `code` / `llm` / `variable` | `in` | `out` | demo 单出口节点 |
| `group` / `comment` | — | — | 纯视觉，不参与执行 |
| `end` | `in` | — | 流程结束 |

**关键决策：原本引擎内置的 `optional` / `recoverable` 全部删除。**
「找不到也继续」变成 `failure → 下一个节点` 的连线；「页面不对就恢复」变成 `mismatch → 恢复子图` 的连线。所有分支都由图决定。

### 节点清单

画布只暴露**引擎能执行**的节点。demo 自带的 12 种里，多数能执行但与本项目无关；
本项目自定义 3 种。

| 节点 | 来源 | 保留 | 理由 |
|---|---|---|---|
| `start` / `end` | demo | ✅ | 流程边界 |
| `mt-action` | **本项目** | ✅ | 唯一能驱动手机的节点：定位 + 点击/输入/滑动/深链 |
| `mt-condition` | **本项目** | ✅ | 要读手机屏幕（页面/元素存在性），demo 的 `condition` 只比较变量 |
| `mt-loop` | **本项目** | ✅ | 容器式循环，重试语义（最大次数 + 间隔 + 退出条件） |
| `condition` | demo | ✅ | 纯变量比较（`ref` + 运算符），与 `mt-condition` 互补 |
| `loop` | demo | ✅ | 数组遍历（`loopFor`），与 `mt-loop` 的重试语义互补 |
| `http` | demo | ✅ | 调**外部**接口。手机操作不走它——那会让用户填 url/body，语义也丢失 |
| `code` | demo | ✅ | QuickJS 沙箱（32MB / 512KB 栈 / 60s），做纯数据变换 |
| `variable` | demo | ✅ | 流程级变量声明 |
| `llm` | demo | ✅ | 调外部 LLM（`apiHost`/`modelName`/`apiKey` 由用户配） |
| `group` / `comment` | demo | ✅ | 纯视觉，不参与执行（`group` 是容器，`comment` 是标注） |
| `multi-condition` | demo | ❌ 移除 | **demo 自己的执行器列表里就没有它**，拖进来必崩 |
| `break` / `continue` | demo | ❌ 移除 | 依赖 demo 的 loop 栈语义，与 `mt-loop` 混用会混乱 |
| `block-start` / `block-end` | demo | ❌ 移除 | 同上，是 demo `loop` 的内部配对节点 |

**关键决策：`mt-*` 用自己的执行器，但它们与 demo 节点走同一套注册 / 表单 / 数据 / 分发机制。**
不做「第二套引擎」——差异只在「这个节点内部调什么」，不在「怎么被调度」。

### 节点数据形状（与 demo 统一）

**所有节点**（含 `mt-*`）的 `data` 遵循 flowgram demo 的同一套形状：

```ts
interface NodeData {
  title: string
  /** 输入值：常量 / 变量引用 / 模板。这是变量系统能工作的前提。 */
  inputsValues: Record<string, FlowValue>
  /** 输入声明（JSON Schema）：驱动变量面板与校验。 */
  inputs: { type: 'object'; properties: Record<string, unknown> }
  /** 输出声明（JSON Schema）：下游节点据此引用本节点的产出。 */
  outputs: { type: 'object'; properties: Record<string, unknown> }
}

/** 一个输入值的三选一来源。 */
type FlowValue =
  | { type: 'constant'; content: string | number | boolean }
  | { type: 'ref'; content: string[] }        // 如 ['submitNote', 'ok']
  | { type: 'template'; content: string }     // 如 '点击{{keyword}}'
```

**为什么必须这样**：旧的裸字段（`data.locate` / `data.act`）只能靠 `resolveText` 做
`ctx.flowParams[key]` 的字符串查表——无法引用上游节点输出，无法插值，且分不清
「这段文字是字面量还是参数名」。`inputsValues` 把来源显式化，歧义消失。

**键名约定：扁平 camelCase，不用点号。**
`locateMode` 而不是 `locate.mode`——因为画布表单用 `Field name="inputsValues.locateMode"`
绑定，键里带点号会和 Field 的点路径语法冲突。所有键名：

| 节点 | 键 |
|---|---|
| `mt-action` | `locateMode` `locateIntent` `locateFallback` `locateVision` `locateStrict` `locatePointX` `locatePointY` `locateRatioX` `locateRatioY` `actKind` `actName` `actUri` `actText` `actInputLocator` `actMatch` `actExtras` `actMin` `actMax` `actDurationMs` `actFromX` `actFromY` `actToX` `actToY` `requires` `settle` `verify` |
| `mt-condition` | `judgeKind` `judgeKey` `judgeExpect` `judgeLocateIntent` `judgeLocateFallback` `judgeLocateVision` `judgeLocateStrict` |
| `mt-loop` | `loopMax` `loopGap` |

### 动作节点配置

沿用现有 `ActionSpec` 的定位与校验概念，去掉 `optional` / `landsOn` / `recoverable`：

- **定位三选一**（`locate.mode`）：
  - `intent`：自然语言描述（「点击发布按钮」），由模型在 UI 树上定位。能见到 UI 树的场景都用它。
  - `point`：绝对坐标（`x`/`y`）。UI 树里看不到的元素（Canvas、WebView、游戏画面）用它。
  - `ratio`：比例坐标（`0`–`1`）。同 `point`，但换机型不失效，**优先选它**。
- 执行：点击 / 输入 / 滑动 / 返回 / 深链 / 自定义
- 校验：页面变化 / 元素存在 / 元素消失 / 输入框等于 / 数值达标 / 自定义
- 循环参数移到 `loop` 节点，动作节点只跑一次

// 绝对定位（精确像素）
"inputsValues": {

### 执行器形状（与 demo 统一）

执行器与 demo 的 `runtime-js` 同形，**不再用 `switch (node.type)` 分发**：

```ts
interface NodeExecutor {
  readonly type: string
  execute(ctx: NodeContext): Promise<NodeResult>
}

interface NodeResult {
  /** 走哪个出口；省略表示唯一出口。 */
  branch?: PortId
  /** 本节点的产出，供下游 `ref` 引用。 */
  outputs: Record<string, unknown>
  /** 失败原因（写进事件流，供 UI 显示）。 */
  reason?: string
}
```

每个节点一个执行器类：`StartExecutor` / `MtActionExecutor` / `MtConditionExecutor` /
`MtLoopExecutor` / `EndExecutor`。引擎只负责「取节点 → 找执行器 → 跑 → 按 branch 选边」，
不认识任何具体节点语义。

### 条件节点配置

三种内置判断，覆盖现有全部隐藏分支：

- `page`：当前页面是否属于某组页面 id（用于「页面不对 → 恢复」）
- `exists`：某元素是否存在（用于「有没有弹窗」）
- `param`：流程参数是否非空（用于「有没有标题 / 有没有图片 / 是否音乐图集」）

### 循环节点配置

- 最大次数
- 每轮间隔区间
- 退出条件（可选：条件节点 id）

### 存法与校验

- 位置：`data/workflows/<flowName>.json`（一图一文件，文件名即流程名）
- 加载时校验：节点 id 唯一、`entry` 指向 `start`、每条边两端存在、端口与源节点类型匹配、除 start 外每个节点至少一条入边、除 end 外每个节点至少一条出边、图内可以有环但必须有 `end` 可达路径
- 校验失败直接抛错，不允许「部分可用」

### 旧模板迁移

现有 4 个模板共 **45 个 `mt-action` + 11 个 `mt-condition`**，需从裸字段迁到 `inputsValues`：

| 旧字段 | 新位置 | 类型 |
|---|---|---|
| `data.locate.intent` | `inputsValues['locate.mode'] = 'intent'` + `inputsValues['locate.intent']` | `constant` |
| `data.locate.fallback` | `inputsValues['locate.fallback']` | `constant` |
| `data.act.kind` | `inputsValues['act.kind']` | `constant` |
| `data.act.text` | `inputsValues['act.text']` | `constant` |
| `data.act.uri` | `inputsValues['act.uri']` | `constant` |
| `data.settle` | `inputsValues['settle']` | `constant`（`'0.5,1.5'`） |
| `data.requires` | `inputsValues['requires']` | `constant`（逗号分隔） |
| `data.judge` | `inputsValues['judge.*']` | 按 `kind` 拆成多个 key |

迁移脚本要求：
- **幂等**：跑两次结果相同（已迁移的节点检测到 `inputsValues` 就跳过）
- **保留 id 与连线**：只改 `data`，不动 `nodes[].id` / `edges[]`
- **备份**：首次运行前把原文件复制到 `data/workflows/.backup/<时间戳>/`
- **干跑**：`--dry-run` 只打印将要改动的节点数与样例

### 执行语义

- 从 `entry` 开始，按当前节点**被选择的端口**找下一条边
- 一个端口有多条边时按数组顺序取第一条（确定性）
- 每次转移计入 `maxSteps`，超限抛错
- 每次节点执行写一条事件：节点 id、端口、耗时、结果

### AI 生成

分两层，缺一不可：

1. **能力清单（skill 文档）**：说明有哪些节点类型、端口、校验方式、页面 id、可用的兜底定位器。模型靠它理解语义。

## Testing Decisions

### 什么算好测试

只测外部行为，不测实现细节：

- ✅ 「图 A→B→C，执行轨迹是 [A,B,C]」
- ✅ 「条件判 true，只走 true 那条边」
- ✅ 「动作失败，走 failure 端口连的节点，不走 success」
- ❌ 「engine.ts 第 42 行调用了 routePort」——测实现细节，重构就碎

### 两层接缝

**接缝一：`runGraph(ctx, graph)` — 端到端路由**

用假 `StepContext`（记录被调用的动作，不碰真机）驱动各种图，断言执行轨迹：

| 用例 | 断言 |
|---|---|
| 线性三节点 | 轨迹 `[A, B, C]` |
| 条件 true | 轨迹只含 true 分支 |
| 条件 false | 轨迹只含 false 分支 |
| 循环 3 次 | 循环体执行 3 次后走 done |
| 动作 failure | 走 failure 端口 |
| 页面 mismatch | 走 mismatch 端口 |
| 到达 end | 立即停止，不再执行后续 |
| 环形图超 `maxSteps` | 抛错并说明超限节点 |
| 端口有多条边 | 取第一条（确定性） |

**接缝二：`executeNode(ctx, node)` — 节点内部**

每种节点单独测，断言返回的端口和副作用：

| 节点 | 断言 |
|---|---|
| `action` | 定位成功 → `success`；定位失败 → `failure`；页面不符 → `mismatch` |
| `condition/page` | 页面在集合内 → `true` |
| `condition/param` | 参数非空 → `true` |
| `loop` | 未达次数 → `body` 且计数 +1；达次数 → `done` |
| `start` / `end` | 返回预期端口，无副作用 |

### 校验层测试

图加载校验：缺入口、边指向不存在的节点、端口与节点类型不匹配、无 `end` 可达路径——每种都要有一条「应当抛错」的测试。

# Test Run 接入（flowgram 运行时接口）

画布上的「Test Run」不跑 flowgram 自带的 `@flowgram.ai/runtime-js`——它只认识
`llm`/`http`/`code`，不认识 `mt-action`，而且跑在浏览器里够不到 ADB。

改为由**内核实现 flowgram 的 5 个运行时接口**，前端只切 `mode:'server'`。

## 5 个端点

前端 `WorkflowRuntimeServerClient` 会自己拼上前缀 `/api`，所以实际路径是：

| 契约 | 方法与路径 | 入参 | 出参 |
|---|---|---|---|
| `TaskValidate` | `POST /api/task/validate` | `{ schema, flowId? }` | `{ valid, errors?: string[] }` |
| `TaskRun` | `POST /api/task/run` | `{ schema, inputs }` | `{ taskID }` |
| `TaskReport` | `GET /api/task/report?taskID=` | — | `{ id, workflowStatus, reports, messages, outputs }` |
| `TaskResult` | `GET /api/task/result?taskID=` | — | 图执行结果 |
| `TaskCancel` | `PUT /api/task/cancel?taskID=` | — | `{ success }` |

`TaskRun` **立即返回 taskID**（异步任务模型），前端靠 `report` 轮询，按
`reports[nodeId].status` 给节点染色。

## 三个必须注意的坑

1. **`errors` 必须是 `string[]`**
   返回 `[{ nodeID, message }]` 这样的对象数组会让前端解析失败、只显示
   "Internal Server Error"，看不出任何原因。

2. **跨域会静默失败**
   前端在 `:3000`、内核对端在 `:7788`，属跨域。缺 CORS 头时浏览器直接拦截
   `OPTIONS` 预检，**内核日志里连请求都看不到**——容易被误判为业务错误。
   内核现在统一在 `sendJson` 加 `access-control-*`，并对 `OPTIONS` 直接 204。

3. **画布的 schema 只有 `{nodes, edges}`**
   不带 `id`/`title`/`data`。`app`（包名、页面表）和 `maxSteps` 是业务知识，
   由内核启动时预加载 `data/flows/*.json`，再按**节点 id 集合**反查匹配
   （≥50% 交集才算同一张图）。`id`/`title` 在校验里可省略。

## 前端配置

# 流程持久化（WorkflowStore）

插件：`packages/core/workflows`（`@myt/workflows`），由 kernel 装配。

## 磁盘布局

```
<dataRoot>/workflows/
├── 小红书发布图文.json
├── 小红书发布视频.json
└── 登录后养号.json
```

**文件名就是用户可见的流程名**，一个流程一个文件。

## 身份设计（关键）

| | 用什么 | 为什么 |
|---|---|---|
| **文件名** | 用户可见的流程名 | 用户在资源管理器里要能分辨；`a3f8c21e-…json` 完全看不懂 |
| **身份标识** | 文件内容里的 `id`（uuid） | 用户改文件名不会让流程「消失」；历史记录、运行日志仍连着 |

```json
{
  "id": "2fd6cbeb-e51d-41ee-b8d5-280fa5cce4f3",
  "nodes": [...],
  "edges": [...],
  "globalVariable": {...}
}
```

## 用户可直接操作文件

程序会正确处理三种「绕过 UI 的操作」：

| 用户操作 | 程序行为 |
|---|---|
| 在资源管理器里**改名** | 重新扫盘按文件名识别，`id` 不变，仍能按 id 找到；列表显示新名字 |
| **复制**文件（产生重复 id） | `list()` 时发现重复，给后出现者重新分配 id 并写回 |
| **删除**文件 | 扫盘时自然消失 |
| 文件**损坏**（非法 JSON） | 跳过该文件，不影响其它流程 |

## 接口

| 方法与路径 | 说明 |
|---|---|
| `GET /api/workflows` | 列表（按修改时间倒序） |
| `POST /api/workflows` `{name}` | 新建空白流程（start + end） |
| `GET /api/workflows/:fileName` | 读完整画布 JSON |
| `PUT /api/workflows/:fileName` | 保存（body 即画布 JSON） |
| `DELETE /api/workflows/:fileName` | 删除 |
| `POST /api/workflows/rename` `{fileName,name}` | 改名（已存在时自动加序号） |
| `POST /api/workflows/duplicate` `{fileName}` | 复制（换新 id） |

**路由顺序**：`/api/workflows/rename` 与 `/duplicate` 必须放在 `startsWith('/api/workflows/')` 分支**之前**，否则会被当成文件名匹配。

## 边界处理

| 情况 | 处理 |
|---|---|
| 名字含 `/ \ : * ? " < > \|` | 替换为 `_` |
| 名字为空 | 回落到「未命名流程」 |
| 名字超长 | 截断到 100 字符 |
| 改名撞名 | 自动加序号（`名字 (2)`），不覆盖 |
| 写盘中断 | 原子写：先写 `.tmp` 再 `rename`，不留半个文件 |

## 测试

`packages/core/workflows/src/workflows.test.ts`，13 个用例覆盖：

- 文件布局（文件名=流程名、id 在内容里、新建含 start+end）
- 用户直接操作文件（改名后仍能按 id 找到、复制产生的重复 id 自动处理、坏文件隔离）
- 改名与复制（id 不变 / 换新 id / 撞名加序号 / 删除移除文件）
- `sanitizeName` 的非法字符、空名、超长

# HTTP 路由注册机制（@myt/webserver）

## 问题

原先 `kernel.ts` 里硬编码 47 个 `if (url.pathname === …)`，任何插件想提供 API
都必须去改 kernel。这违背 ADR-0001「业务全部写成插件」。

## 方案

```
packages/core/webserver/   →  WebServer extends Service，服务键 ctx.http
                             只做：监听、分发、CORS、JSON、错误收敛
packages/core/workflows/src/api.ts  →  WorkflowApi 在 [Service.init] 里自己注册路由
```

内核完全不认识 `/api/workflows`。

## 插件写法

```ts
export class WorkflowApi extends Service {
  /** 缺 inject 会报：cannot get property "x" without inject */
  static inject = ['workflows', 'http']

  [Service.init](): void {
    this.ctx.http.get('/api/workflows', () => this.ctx.workflows.list())
    this.ctx.http.prefix('GET', '/api/workflows/:file', (c) => this.ctx.workflows.load(c.params.file))
  }
}
```

## 路由优先级（关键）

**精确路由永远优先于前缀路由**，与注册顺序无关（实现上分两轮匹配）。
但仍建议先写精确路由，可读性更好：

```ts
ctx.http.post('/api/workflows/rename', …)        // 精确
ctx.http.prefix('GET', '/api/workflows/:file')   // 前缀
```

## 渐进迁移策略

旧 47 个路由**整体挂在 `setFallback` 上**，零风险：

```ts
const legacyRoutes = async (req, res) => { /* 原 1255 行路由链原样保留 */ }
ctx.http.setFallback((context) => legacyRoutes(context.req, context.res))
```

新功能走 `ctx.http`，旧路由逐个迁走，迁完删除整块。

## 处理器契约

- 返回值 → 序列化为 JSON
- `throw new HttpError(404, '…')` → 用该状态码
- 抛普通错误 → 502
- 处理器自己写响应（SSE）→ 框架不重复写

## CORS

默认开启。前端 `:3000`、内核 `:7788`，缺 CORS 头时浏览器拦 `OPTIONS` 预检，
**内核日志连请求都看不到**——这个坑很隐蔽。

## 已知限制

`WebServer` 的 fallback 与插件路由共用同一个 `ServerResponse`；
静态文件服务仍在旧链里，迁移时需注意 `res.writeHead` 与 `sendJson` 不混用。

## 两种模式

| URL | 行为 |
|---|---|
| `/?flow=流程名.json` | 从内核加载，编辑后自动保存回去 |
| `/`（无参数） | 用内置示例数据（`initial-data.ts`），不保存 |

| 位置 | 触发 |
|---|---|
| `use-editor-props.tsx` 的 `onContentChange` | 内容变更，防抖 1s |
| `save.tsx` 的 Save 按钮 | 手动 |
| `testrun-button` | 点 Test Run 前先存（不能跑旧图） |

## 数据覆盖 bug（已修，重要）

**现象**：拖动节点 → 自动保存成功 → 刷新页面 → **磁盘被重置回初始位置**。

**原因**：画布初始化时会触发 `onContentChange`（把加载的数据当成「变更」），
用初始位置覆盖了磁盘上用户的改动。

**修复**（两道保险）：

```ts
// 1. 加载后 2s 内忽略自动保存（那是画布初始化，不是用户改动）
if (Date.now() - loadedAt.current < 2000) return;

// 2. 内容没变就不写盘（幂等，也挡住 toJSON 字段顺序抖动）
const snapshot = JSON.stringify(next);
if (snapshot === lastSaved.current) return;
```

**验证**：拖动 → 磁盘更新 → 刷新 → 磁盘保持不变。

## 前置：Test Run 必须先保存

`testrun-button` 在打开面板前 `await workflow.save()`。
否则用户在画布上改了节点，点 Test Run 跑的还是内核里的旧图。

## 自定义动作的拆解（2026-11-02）

### 背景

原来「做什么」里有一项 **自定义动作**：填一个名字（如 `waitGallery`），
引擎去业务包的 `XHS_ACTIONS` 里查函数执行。**图上看是一个黑盒**——
一个 `waitGallery` 里揉了 4 件事（跳个人页、跳发布页、轮询等相册、失败重试），
出问题不知道卡在哪一步。

### 处理：删掉自定义动作，改用原语

`actKind: 'custom'` 及 `XHS_ACTIONS` 全部移除。

**新增两个等待原语**（原来缺的正是这类）：

| 原语 | 参数 | 行为 |
|---|---|---|
| **等页面出现** | `actPages`（页面 id，逗号分隔）、`actTimeout` | 轮询 `currentPage`，落在任一页面即成功，超时走 `failure` 端口 |
| **等元素出现** | `actLocateIntent`、`actTimeout` | 轮询定位，出现即成功，超时走 `failure` |

超时走 `failure` 端口而不是抛错——**重试由连线表达**，不在函数里写 `for` 循环。

### 现有原语全集（14 种）

| 类别 | 原语 |
|---|---|
| 定位动作 | 点击、输入文字 |
| 设备动作 | 滑动、按返回键、打开链接、设备命令(adb) |
| 等待 | 等待(秒)、**等页面出现**、**等元素出现** |
| 文件/应用 | 推送文件、推送到相册、安装应用、启用输入法 |

### 已拆解的节点

`发布图文笔记` 的「打开发布页并等相册」拆成三步：

```
跳个人页 (openUri: xhsdiscover://profile)
   ↓ success
打开发布页 (openUri: xhsdiscover://post_note/)
   ↓ success
等相册出现 (waitPage: album,photo-picker,permission / 15s)
   ↓ failure            ↓ success
  end                   check-permission
```

原来藏在函数里的「5 轮重试」现在可以**用连线画出来**（failure 端口连回上一步），
图上一眼能看出卡在哪。

### 全部拆完（2026-11-02）

新增 3 个原语，把剩下含算法的动作也变成可见节点：

| 新原语 | 参数 | 说明 |
|---|---|---|
| ~~点（按定位器）~~ | — | **已删除**：定位器名对用户是黑盒，改用「点（按文字）」 |
| **点（按文字）** | `actTexts` | 给一组候选文案，找到哪个点哪个 |
| **按数量选图** | `actCount`、`actMaxScroll` | 数已选中的图，不够就点下一张，滚到底仍不够则失败 |

「按数量选图」的**算法在通用引擎里**（数选中数、逐个点、滚动补选）；
业务包只提供「哪些是可点的图片格」（`runtime.gallery`）——
各 App 相册结构不同，这一层必须由业务给。

### 迁移结果

| 原 custom 动作 | 拆成 |
|---|---|
| `waitGallery` | 跳个人页 → 打开发布页 → 等相册出现 |
| `pickImages` | 按数量选图（1 个节点） |
| `submitNote` | 点（按定位器）→ `getPublishButtonPosition` |
| `verifyPublished` | 回个人页 → 下拉刷新 → 条件「有笔记或草稿吗」 |
| `openThoughtPage` | 打开链接（深链） |
| `saveArticleDraft` | 按返回键 → 等元素「存草稿按钮」→ 点（按文字）`存草稿,确定` |

三个模板里 **custom 节点全部清零**（原 11 个），悬空边 0、自环 0。

### 引擎与业务的职责边界

| 层 | 负责 |
|---|---|
| 通用引擎 | 选图的**算法**、等页面/等元素的**轮询**、按文字找点 |
| 业务包 | 定位器（按钮在哪）、`gallery`（图片格在哪）、深链、页面表 |

这样图上每个节点都在做「一件事」，且都能被单独观察和失败。

### 等待与重试（2026-11-02 补齐）

拆成原语后暴露一个新问题：**原来藏在自定义动作里的 sleep 和重试没有了**。

现在两者都是节点上的字段，由**引擎统一实现**（不是每个动作自己写循环）：

| 字段 | 位置 | 行为 |
|---|---|---|
| **执行后等待** `settle` | 所有动作节点 | 完成后在给定区间内随机等待（如 `1,2`） |
| **失败重试次数** `retries` | 所有节点 | `failure` / `mismatch` 端口前自动重跑几次 |
| **重试间隔** `retryGap` | 所有节点 | 两次重试之间随机等 1–2 倍该值 |

实现位置：`executeNode`（节点执行入口）——所以**所有节点类型都自动具备重试**，
不需要每个动作各自实现。重试前会 `invalidateSnapshot`，避免读到旧界面。

模板已补齐关键节点的策略：

| 节点 | 执行后等待 | 重试 |
|---|---|---|
| 跳个人页 / 打开发布页 | 1.5–3s | — |
| 等相册出现 | — | 2 次 / 2s |
| 按数量选图 | 0.5–1s | 1 次 / 2s |
| 点发布/存草稿 | 1–2s | 2 次 / 2s |
| 回个人页 + 下拉刷新 | 1.5–3s | — |
| 校验「有笔记或草稿吗」 | — | 2 次 / 3s |
| 存草稿三步 | 0.5–2.5s | 等元素/点按钮各 1–2 次 |

实测（单元测试）：`retries=2` 且第 2 次成功时，定位器被调用 **2 次**、结果 `success`；
`retries` 未填时只调用 **1 次**、结果 `failure`。

### 为什么删掉「点（按定位器）」（2026-11-02）

「点（按定位器）」的参数是 `getPublishButtonPosition` 这种名字——
用户看到它不知道点哪里，而背后是**写死的节点路径** `[[0,0,0,0,0,0,0,3,0,1]]`，
App 改版就失效，且失败时只报「定位器找不到目标」，排查不到原因。

换成「点（按文字）」，参数是 `发布笔记,存草稿`——**界面上看得见的字**。

| | 按定位器 | 按文字 |
|---|---|---|
| 参数 | `getPublishButtonPosition` | `发布笔记,存草稿` |
| 用户看得懂吗 | ❌ | ✅ |
| App 改版 | 路径失效，难排查 | 文案变了会明确报「界面上没有这些文字」 |
| 适配其他 App | 需要新写定位器 | 换个词就行 |

现在引擎里**没有任何按定位器点击的入口**，动作原语全部以「界面上看得见的文字/坐标」为参数。


### 提交动作的最终形态（2026-11-02）

之前我把「按文字点击」做成独立动作类型（`tapText`），与已有的
「怎么找 = 按文字找 / 找什么 / 做什么 = 点击」重复且割裂。已删除。

**统一形态**（所有定位类动作）：

```
怎么找：按文字找 / 按屏幕比例 / 按像素坐标
找什么：（对应的值）
做什么：点击 / 输入文字
```

**存草稿**不是一步——原 `submitNote(mode='save')` 是两步：

```
点「存草稿」  →  等 1–2s  →  点「确定」（确认弹窗）  →  回个人页校验
```

三个模板已按此拆成 `submit` + `submit-confirm` 两个节点，
失败端口都接到 `end`。
