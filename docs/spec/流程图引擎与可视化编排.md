# 流程图引擎与可视化编排（Spec）

> 状态：图引擎 + 三个流程迁移完成（22 个单元测试 + 三流程真机跑通），待做画布 UI
> 关联：[CONTEXT.md](../../CONTEXT.md)（术语）、[ADR-0001](../adr/ADR-0001-architecture-baseline.md)（架构基线）

## Problem Statement

现在的流程是**平铺的动作数组**，三分支逻辑全部隐藏在代码里，用户在 UI 上看不到、也改不了：

| 隐藏在代码里的行为 | 位置 | 用户看到什么 |
|---|---|---|
| 没有标题就跳过 | `if (!input.title) return` | 什么都看不到 |
| 没有图片就跳过 | `if (input.imagePaths.length === 0) return` | 什么都看不到 |
| 不是音乐图集就跳过 | `if (!input.musicImg) return` | 什么都看不到 |
| 找不到元素就跳过（`optional`） | 引擎内置 | 一个布尔开关 |
| 页面不对就恢复（`recoverable`） | 引擎内置 | 一个布尔开关 |
| 失败就整单停 | `if (!result.ok) throw` | 看不到 |

**后果**：

1. 改流程必须改代码、重新构建、重新跑真机验证（一轮 90 秒）。
2. 业务人员无法自己调整流程顺序或分支。
3. 出了问题是哪一步、走了哪条路，只能翻日志。
4. 加新 App（抖音、快手）必须写代码。

## Solution

把流程从「平铺数组」改成**有向图**，并在 UI 上以画布形式可视化编辑：

- 每个**动作节点**都有独立端口：`success` / `failure` / `mismatch`（页面不对）
- **条件节点**（`true` / `false`）和**循环节点**（`body` / `done`）承担原本隐藏在代码里的分支
- 流程定义存成 **JSON 文件**（`data/flows/*.json`），运行时加载，改流程不用改代码
- 画布直接读写这些 JSON，节点配置通过属性面板可视化编辑
- **现有 UI 整体重做**，用 `design-taste` 技能的 app screen 规范重新设计

## 界面文案规范

UI 最终给业务人员看，**不用专业术语当标签**。分三层：

| 层 | 语言 | 例子 |
|---|---|---|
| **界面标签、节点名** | 中文大众词 | 「填写标题」而不是 `fill-title`；「打开笔记页」而不是 `open-post-editor` |
| **悬浮释义** | 中文解释专业概念 | 鼠标悬浮「恢复规则」→「页面不对时自动做什么」 |
| **代码标识符** | 英文 | `FlowGraph`、`actionNode`、`portId`（与 STYLE.md §3 一致） |

**释义放在哪**：每个专业词在界面上都有 `title` 属性（浏览器原生悬浮提示）或自绘 tooltip，内容是一句话中文解释 + 一个例子。不需要用户先学概念。

**已知需要释义的词**：

| 界面用词 | 释义 |
|---|---|
| 动作 | 在手机上做一件事：点一下、输文字、滑一下 |
| 端口 | 这一步走完后，下一条路往哪走 |
| 成功 / 失败 / 页面不对 | 三种结果，分别连到不同的下一步 |
| 条件 | 先判断一下，再决定走哪条路 |
| 循环 | 重复做几次 |
| 定位 | 怎么在屏幕上找到要点的东西 |
| 兜底 | 自动找失败时，用预先写死的位置再试一次 |
| 恢复 | 页面跑到别处了，怎么退回来 |
| 页面表 | 这个 App 有哪些界面，各自怎么认出来 |
| 轮数 | 最多试几次 |
| 间隔 | 每次之间等多久 |

## User Stories

### 引擎与数据

1. 作为流程作者，我想把流程定义成 JSON 文件，这样改流程不用重新编译。
2. 作为流程作者，我想让每个动作都有 `success` / `failure` / `mismatch` 三个出口，这样失败后走哪条路是我决定的，不是引擎决定的。
3. 作为流程作者，我想用条件节点表达「有标题才填标题」，这样这个判断在画布上看得见。
4. 作为流程作者，我想用循环节点表达「最多重试 6 轮」，这样重试次数和循环体都可以在画布上看到。
5. 作为流程作者，我想让 JSON 在加载时被校验（缺字段、连到不存在的节点、有环），这样错误在启动时暴露，而不是跑到一半才崩。
6. 作为流程作者，我想让图有明确的入口和出口，这样执行路径唯一确定。

### 执行

7. 作为运维人员，我想看到每一步实际走了哪个端口，这样出问题能定位是哪条分支。
8. 作为运维人员，我想让节点失败后按图上的连线继续，而不是中断整单，这样「失败就回退首页重来」这类策略也可以画出来。
9. 作为运维人员，我想给图设最大执行步数，这样环形连线不会跑死。
10. 作为运维人员，我想让每个节点的执行耗时和结果写入事件流，这样能看瓶颈在哪。
11. 作为运维人员，我想让页面不匹配时走 `mismatch` 端口，这样能画出「页面不对 → 恢复 → 重试」的子图。

### 画布

12. 作为流程作者，我想在画布上拖拽节点、连线，这样不用写 JSON。
13. 作为流程作者，我想点开节点看到它的全部配置，这样不用查文档。
14. 作为流程作者，我想在画布上看到每个节点的类型一眼可辨（动作/条件/循环/开始/结束），这样不用点开就知道结构。
15. 作为流程作者，我想在画布上直接看出哪条边是 `success`、哪条是 `failure`，这样不用点开节点。
16. 作为流程作者，我想在运行后看到画布上每个节点染上执行状态，这样一眼看出跑到哪、卡在哪。
17. 作为流程作者，我想从画布上直接运行某个节点开始，这样调试单步更快。
18. 作为流程作者，我想让画布自动布局，这样打开就能看清结构。

### 界面文案

19. 作为业务人员，我想在画布上看到「填写标题」这样的中文节点名，这样不用懂代码也能看懂流程。
20. 作为业务人员，我想把鼠标悬浮在专业词上看到一句中文解释，这样不用先学概念。
21. 作为业务人员，我想让属性面板的字段标签也全是中文，这样打开就能填。
22. 作为开发者，我想让代码里的标识符保持英文，这样和现有代码风格一致、便于排查。

### UI 重做

23. 作为业务人员，我想看到一套重新设计的界面，而不是现在这套静态 HTML，这样看着像个产品而不是脚本。
24. 作为业务人员，我想让设备农场、流程画布、运行记录在同一个应用里切换，这样不用开多个窗口。
25. 作为业务人员，我想让界面在 1280 宽和 1920 宽下都不挤，这样不同显示器都能用。
26. 作为开发者，我想让新 UI 的节点、面板、表格样式统一，这样加新页面不用重新发明样式。

### AI 生成

27. 作为流程作者，我想用自然语言描述需求，让 AI 生成画布上的节点和连线。
28. 作为流程作者，我想让 AI 知道我们有哪些动作、哪些校验、哪些页面 id，这样它不会生成不存在的字段。
29. 作为流程作者，我想让 AI 生成的图直接通过校验，这样不用手工修 schema 错误。
30. 作为流程作者，我想让 AI 只增改我圈选的那部分节点，这样不用重新生成整张图。

### 迁移与兼容

31. 作为开发者，我想让现有三个流程（图文/文字/长文）都迁移成 JSON 图，这样只剩一套执行模型。
32. 作为开发者，我想让迁移后的三个流程真机跑通，证明图引擎和原来的行为等价。
33. 作为开发者，我想删掉旧的 `ActionSpec[]` 执行路径，这样不会有第二套语义。

## Implementation Decisions

### 图数据结构

图是「节点 + 连线」的有向图，节点带画布坐标（供 UI 渲染）。

```ts
interface FlowGraph {
  id: string
  title: string
  nodes: FlowNode[]
  edges: FlowEdge[]
  /** 业务配置（画布 JSON 的 `data` 扩展位）。 */
  data: {
    /** 目标 App 配置：包名、首页深链、页面表、恢复规则。 */
    app: AppConfig
    /** 最大执行步数，防止环形连线跑死。 */
    maxSteps: number
  }
  /** 入口节点 id；省略时自动取唯一的 start 节点。 */
  entry?: string
}

interface FlowNode {
  id: string
  /** 节点类型（与画布 `node.type` 完全一致）。 */
  type: 'start' | 'mt-action' | 'mt-condition' | 'mt-loop' | 'loop' | 'end'
  /** 画布元信息。 */
  meta: { position: { x: number; y: number } }
  /** 业务数据。 */
  data: {
    /** 中文展示名，给用户看。 */
    title?: string
    requires?: string[]
    locate?: LocateConfig
    act?: ActConfig
    verify?: VerifyConfig
    settle?: [number, number]
    judge?: ConditionNodeConfig
    loopFor?: LoopNodeConfig
    [key: string]: unknown
  }
  /** 循环容器的子节点。 */
  blocks?: FlowNode[]
}

interface FlowEdge {
  sourceNodeID: string
  sourcePortID: PortId
  targetNodeID: string
}

type PortId = 'out' | 'success' | 'failure' | 'mismatch' | 'true' | 'false' | 'body' | 'done'
```

### 端口契约

| 节点类型 | 入口 | 出口 | 语义 |
|---|---|---|---|
| `start` | — | `out` | 流程入口，只能有一个 |
| `mt-action` | `in` | `success` / `failure` / `mismatch` | success = 动作成功；failure = 定位失败或校验不过；mismatch = 前置页面不符 |
| `mt-condition` | `in` | `true` / `false` | 条件成立走 true |
| `mt-loop` | `in` | `done` | 容器式循环，循环体在 `blocks` 里 | 未达次数走 body，达次数走 done |
| `end` | `in` | — | 流程结束 |

**关键决策：原本引擎内置的 `optional` / `recoverable` 全部删除。**
「找不到也继续」变成 `failure → 下一个节点` 的连线；「页面不对就恢复」变成 `mismatch → 恢复子图` 的连线。所有分支都由图决定。

### 动作节点配置

沿用现有 `ActionSpec` 的定位与校验概念，去掉 `optional` / `landsOn` / `recoverable`：

- 定位：意图描述 + 确定性兜底 + 严格模式开关
- 执行：点击 / 输入 / 滑动 / 返回 / 深链 / 自定义
- 校验：页面变化 / 元素存在 / 元素消失 / 输入框等于 / 数值达标 / 自定义
- 循环参数移到 `loop` 节点，动作节点只跑一次

### 条件节点配置

三种内置判断，覆盖现有全部隐藏分支：

- `page`：当前页面是否属于某组页面 id（用于「页面不对 → 恢复」）
- `exists`：某元素是否存在（用于「有没有弹窗」）
- `param`：流程参数是否非空（用于「有没有标题 / 有没有图片 / 是否音乐图集」）

### 循环节点配置

- 最大次数
- 每轮间隔区间
- 退出条件（可选：条件节点 id）

### 存法与校验

- 位置：`data/flows/<flowId>.json`
- 加载时校验：节点 id 唯一、`entry` 指向 `start`、每条边两端存在、端口与源节点类型匹配、除 start 外每个节点至少一条入边、除 end 外每个节点至少一条出边、图内可以有环但必须有 `end` 可达路径
- 校验失败直接抛错，不允许「部分可用」

### 执行语义

- 从 `entry` 开始，按当前节点**被选择的端口**找下一条边
- 一个端口有多条边时按数组顺序取第一条（确定性）
- 每次转移计入 `maxSteps`，超限抛错
- 每次节点执行写一条事件：节点 id、端口、耗时、结果

### UI 重做

**现状**：`packages/client/ui/index.html`（372 行）+ `login.html`（2046 行），纯静态 HTML，无框架，样式内联。

**决策：旧 UI 保留但隐藏，新 UI 作为唯一入口。**

- 旧文件**不删除**（`index.html` / `login.html` 原样保留），只是不再被任何路由/菜单指向
- 新 UI 放在独立目录，作为默认工作面
- 想回看旧界面时，直接打开旧 HTML 文件即可（不占入口）
- 内核里原先把 `/` 和 `/login` 指向旧 UI（两个路由，读 `uiDir/index.html` 与 `uiDir/login.html`），
  改为指向新 UI 目录；旧目录不删、不挂路由
- `MYT_UI_DIR` 环境变量语义不变：指向哪个目录就服务哪个 UI

设计流程按 `design-taste` 技能走，且**必须用 app screen 规范**（`references/app-screens.md`，85 KB），不是落地页规范——我们是「人们在里面工作的界面」，不是营销页。

设计步骤：

1. **出方向**：`draw.mjs --app --sector dev-tool --brief "<产品描述>"` 发三个方向，选一个
2. **定细节**：脚本再发字体系统、配色、面板/表格/控件的样式
3. **实现**：按 `assets/app.css` 的组件样式建页面；用 `assets/charts.js` 画运行统计
4. **检查**：`inspect.mjs --app` 用真实浏览器验规则（间距、对比度、字号下限 13px、正文 16px+）
5. **看效果**：三种宽度截图 → 按 `references/critique.md` 评审 → 改了再看

页面清单（都要重做）：

| 页面 | 内容 | 关键设计点 |
|---|---|---|
| 设备农场 | 宿主/坑位/容器表格、状态筛选、启动停止 | 表格只有横线，数字右对齐，状态用文字不用彩点 |
| 流程画布 | 节点编辑、连线、属性面板、运行状态染色 | **真·无限画布**（见下） |
| 运行记录 | 事件流、每步耗时、失败节点 | 等宽数字，时间戳右对齐 |
| AI 对话 | 左侧对话、右侧实时渲染画布 | 对话气泡不用彩色 |

**画布必须是真·无限画布。** 实测三张图的纵向跨度都是 2400px、横向最多 400px，
加节点尺寸后需要 2600px × 738px；屏幕可视区约 800×900，不缩放只能看到 1/3。

| 能力 | 规格 |
|---|---|
| 平移 | 拖拽空白区；滚轮纵向、Shift+滚轮横向 |
| 缩放 | 25%–150%，默认 100% |
| 自适应全图 | 按节点包围盒算缩放比，留 48px 边距，居中 |
| 缩略图 | 右下角 120×80，显示全图轮廓 + 当前视口框 |
| 分级可读性 | ≥75% 显示指标；50-75% 隐藏指标；25-50% 只显示标题；<25% 只显示色块 |

详细规格见 `界面设计规范.md`。

技术选型在实施阶段定；约束是「一套设计 token（颜色、字号、间距、圆角）贯穿所有页面」。

### AI 生成

分两层，缺一不可：

1. **能力清单（skill 文档）**：说明有哪些节点类型、端口、校验方式、页面 id、可用的兜底定位器。模型靠它理解语义。
2. **JSON Schema 校验**：图定义导出为 JSON Schema，模型输出必须通过校验才能落盘。结构错误由校验层拦截，不靠提示词。

对话界面参考 DeepSeek 那种「左侧对话、右侧实时渲染画布」的布局。

## Testing Decisions

### 什么算好测试

只测外部行为，不测实现细节：

- ✅ 「图 A→B→C，执行轨迹是 [A,B,C]」
- ✅ 「条件判 true，只走 true 那条边」
- ✅ 「动作失败，走 failure 端口连的节点，不走 success」
- ❌ 「engine.ts 第 42 行调用了 routePort」——测实现细节，重构就碎

### 两层接缝

**接缝一：`runGraph(ctx, graph)` — 端到端路由**

用假 `StepContext`（记录被调用的动作，不碰真机）驱动各种图，断言执行轨迹：

| 用例 | 断言 |
|---|---|
| 线性三节点 | 轨迹 `[A, B, C]` |
| 条件 true | 轨迹只含 true 分支 |
| 条件 false | 轨迹只含 false 分支 |
| 循环 3 次 | 循环体执行 3 次后走 done |
| 动作 failure | 走 failure 端口 |
| 页面 mismatch | 走 mismatch 端口 |
| 到达 end | 立即停止，不再执行后续 |
| 环形图超 `maxSteps` | 抛错并说明超限节点 |
| 端口有多条边 | 取第一条（确定性） |

**接缝二：`executeNode(ctx, node)` — 节点内部**

每种节点单独测，断言返回的端口和副作用：

| 节点 | 断言 |
|---|---|
| `action` | 定位成功 → `success`；定位失败 → `failure`；页面不符 → `mismatch` |
| `condition/page` | 页面在集合内 → `true` |
| `condition/param` | 参数非空 → `true` |
| `loop` | 未达次数 → `body` 且计数 +1；达次数 → `done` |
| `start` / `end` | 返回预期端口，无副作用 |

### 校验层测试

图加载校验：缺入口、边指向不存在的节点、端口与节点类型不匹配、无 `end` 可达路径——每种都要有一条「应当抛错」的测试。

### 先例

`packages/device/device/src/ui-locate.test.ts`：vitest + 纯函数 + 假输入，不碰真机。新测试沿用这个形态。

### 真机验证

图引擎单元测试通过后，三个流程各跑一次真机，结果必须与迁移前等价：

| 流程 | 迁移前基线 |
|---|---|
| 图文 | 15/15 |
| 文字 | 12/12 |
| 长文 | 11/11 |

### UI 验证

UI 没有自动化测试。用 `design-taste` 的检查流程代替：`inspect.mjs --app` 验规则 + 三宽度截图人工评审。新 UI 上线前必须把四个页面都走一遍。

## Out of Scope

- **画布库的选型与实现细节**（React Flow vs 自绘）——实施阶段定
- **AI 对话界面的具体实现**——本 spec 只定「能力清单 + JSON Schema」两层
- **多版本/多分支流程管理**（草稿、发布、回滚）
- **流程间复用**（子图/子流程调用）
- **并行分支**（同时跑两条边）——目前单线程顺序执行
- **旧 `ActionSpec[]` 的兼容层**——按决策直接删除，不做双轨
- **移动端适配**——只考虑 1280 以上的桌面宽度
- **删除旧 UI**——旧文件保留作参考，不删

| `locators/*.ts` 的确定性定位器 | 保留，作为动作节点的兜底 |
| 三个 `flows/*.ts` | 改写成 `data/flows/*.json` |
| `packages/client/ui/*.html` | **保留但隐藏**，不再作为入口；新 UI 用 design-taste 的 app screen 规范另建 |

### 为什么先做引擎再画画布

没有能跑的图引擎，画布做出来无法验证——节点拖得再好看，执行对了没有不知道。
所以顺序是：图数据结构 → 图引擎 + 测试 → 三个流程迁移 → 真机验证 → 画布 UI → AI 生成。

### 一个已知的迁移风险

现有 `publish-image.ts` 里 `skip-image-editor` 那一步用 `recoverTo` 做了「预览页 → 编辑页 → 发布页」的多跳推进。迁移时必须画成显式节点序列，不能塞回一个 `action` 节点里——否则又变回隐式逻辑。

# Test Run 接入（flowgram 运行时接口）

画布上的「Test Run」不跑 flowgram 自带的 `@flowgram.ai/runtime-js`——它只认识
`llm`/`http`/`code`，不认识 `mt-action`，而且跑在浏览器里够不到 ADB。

改为由**内核实现 flowgram 的 5 个运行时接口**，前端只切 `mode:'server'`。

## 5 个端点

前端 `WorkflowRuntimeServerClient` 会自己拼上前缀 `/api`，所以实际路径是：

| 契约 | 方法与路径 | 入参 | 出参 |
|---|---|---|---|
| `TaskValidate` | `POST /api/task/validate` | `{ schema, flowId? }` | `{ valid, errors?: string[] }` |
| `TaskRun` | `POST /api/task/run` | `{ schema, inputs }` | `{ taskID }` |
| `TaskReport` | `GET /api/task/report?taskID=` | — | `{ id, workflowStatus, reports, messages, outputs }` |
| `TaskResult` | `GET /api/task/result?taskID=` | — | 图执行结果 |
| `TaskCancel` | `PUT /api/task/cancel?taskID=` | — | `{ success }` |

`TaskRun` **立即返回 taskID**（异步任务模型），前端靠 `report` 轮询，按
`reports[nodeId].status` 给节点染色。

## 三个必须注意的坑

1. **`errors` 必须是 `string[]`**
   返回 `[{ nodeID, message }]` 这样的对象数组会让前端解析失败、只显示
   "Internal Server Error"，看不出任何原因。

2. **跨域会静默失败**
   前端在 `:3000`、内核对端在 `:7788`，属跨域。缺 CORS 头时浏览器直接拦截
   `OPTIONS` 预检，**内核日志里连请求都看不到**——容易被误判为业务错误。
   内核现在统一在 `sendJson` 加 `access-control-*`，并对 `OPTIONS` 直接 204。

3. **画布的 schema 只有 `{nodes, edges}`**
   不带 `id`/`title`/`data`。`app`（包名、页面表）和 `maxSteps` 是业务知识，
   由内核启动时预加载 `data/flows/*.json`，再按**节点 id 集合**反查匹配
   （≥50% 交集才算同一张图）。`id`/`title` 在校验里可省略。

## 前端配置

`packages/client/app/src/hooks/use-editor-props.tsx`：

```ts
createRuntimePlugin({
  mode: 'server',
  serverConfig: { domain: '127.0.0.1', port: 7788, protocol: 'http' },
})
```

## 上下文构造共用

`@myt/flow` 导出 `createStepContext(device, runs, input)`。步骤引擎（`FlowRunner`）
和图引擎（`runGraph`）都走它——两套引擎必须看到一致的 `StepContext`：同样的快照
缓存、同样的取消语义、同样的定位回退记录。各写一份会漂移。

`StepContext.invalidateSnapshot()` 用于步骤之间丢弃旧快照（上一步已改变界面）。

# 流程持久化（WorkflowStore）

插件：`packages/core/workflows`（`@myt/workflows`），由 kernel 装配。

## 磁盘布局

```
<dataRoot>/workflows/
├── 小红书发布图文.json
├── 小红书发布视频.json
└── 登录后养号.json
```

**文件名就是用户可见的流程名**，一个流程一个文件。

## 身份设计（关键）

| | 用什么 | 为什么 |
|---|---|---|
| **文件名** | 用户可见的流程名 | 用户在资源管理器里要能分辨；`a3f8c21e-…json` 完全看不懂 |
| **身份标识** | 文件内容里的 `id`（uuid） | 用户改文件名不会让流程「消失」；历史记录、运行日志仍连着 |

```json
{
  "id": "2fd6cbeb-e51d-41ee-b8d5-280fa5cce4f3",
  "nodes": [...],
  "edges": [...],
  "globalVariable": {...}
}
```

## 用户可直接操作文件

程序会正确处理三种「绕过 UI 的操作」：

| 用户操作 | 程序行为 |
|---|---|
| 在资源管理器里**改名** | 重新扫盘按文件名识别，`id` 不变，仍能按 id 找到；列表显示新名字 |
| **复制**文件（产生重复 id） | `list()` 时发现重复，给后出现者重新分配 id 并写回 |
| **删除**文件 | 扫盘时自然消失 |
| 文件**损坏**（非法 JSON） | 跳过该文件，不影响其它流程 |

## 接口

| 方法与路径 | 说明 |
|---|---|
| `GET /api/workflows` | 列表（按修改时间倒序） |
| `POST /api/workflows` `{name}` | 新建空白流程（start + end） |
| `GET /api/workflows/:fileName` | 读完整画布 JSON |
| `PUT /api/workflows/:fileName` | 保存（body 即画布 JSON） |
| `DELETE /api/workflows/:fileName` | 删除 |
| `POST /api/workflows/rename` `{fileName,name}` | 改名（已存在时自动加序号） |
| `POST /api/workflows/duplicate` `{fileName}` | 复制（换新 id） |

**路由顺序**：`/api/workflows/rename` 与 `/duplicate` 必须放在 `startsWith('/api/workflows/')` 分支**之前**，否则会被当成文件名匹配。

## 边界处理

| 情况 | 处理 |
|---|---|
| 名字含 `/ \ : * ? " < > \|` | 替换为 `_` |
| 名字为空 | 回落到「未命名流程」 |
| 名字超长 | 截断到 100 字符 |
| 改名撞名 | 自动加序号（`名字 (2)`），不覆盖 |
| 写盘中断 | 原子写：先写 `.tmp` 再 `rename`，不留半个文件 |

## 测试

`packages/core/workflows/src/workflows.test.ts`，13 个用例覆盖：

- 文件布局（文件名=流程名、id 在内容里、新建含 start+end）
- 用户直接操作文件（改名后仍能按 id 找到、复制产生的重复 id 自动处理、坏文件隔离）
- 改名与复制（id 不变 / 换新 id / 撞名加序号 / 删除移除文件）
- `sanitizeName` 的非法字符、空名、超长

# HTTP 路由注册机制（@myt/webserver）

## 问题

原先 `kernel.ts` 里硬编码 47 个 `if (url.pathname === …)`，任何插件想提供 API
都必须去改 kernel。这违背 ADR-0001「业务全部写成插件」。

## 方案

```
packages/core/webserver/   →  WebServer extends Service，服务键 ctx.http
                             只做：监听、分发、CORS、JSON、错误收敛
packages/core/workflows/src/api.ts  →  WorkflowApi 在 [Service.init] 里自己注册路由
```

内核完全不认识 `/api/workflows`。

## 插件写法

```ts
export class WorkflowApi extends Service {
  /** 缺 inject 会报：cannot get property "x" without inject */
  static inject = ['workflows', 'http']

  [Service.init](): void {
    this.ctx.http.get('/api/workflows', () => this.ctx.workflows.list())
    this.ctx.http.prefix('GET', '/api/workflows/:file', (c) => this.ctx.workflows.load(c.params.file))
  }
}
```

## 路由优先级（关键）

**精确路由永远优先于前缀路由**，与注册顺序无关（实现上分两轮匹配）。
但仍建议先写精确路由，可读性更好：

```ts
ctx.http.post('/api/workflows/rename', …)        // 精确
ctx.http.prefix('GET', '/api/workflows/:file')   // 前缀
```

## 渐进迁移策略

旧 47 个路由**整体挂在 `setFallback` 上**，零风险：

```ts
const legacyRoutes = async (req, res) => { /* 原 1255 行路由链原样保留 */ }
ctx.http.setFallback((context) => legacyRoutes(context.req, context.res))
```

新功能走 `ctx.http`，旧路由逐个迁走，迁完删除整块。

## 处理器契约

- 返回值 → 序列化为 JSON
- `throw new HttpError(404, '…')` → 用该状态码
- 抛普通错误 → 502
- 处理器自己写响应（SSE）→ 框架不重复写

## CORS

默认开启。前端 `:3000`、内核 `:7788`，缺 CORS 头时浏览器拦 `OPTIONS` 预检，
**内核日志连请求都看不到**——这个坑很隐蔽。

## 已知限制

`WebServer` 的 fallback 与插件路由共用同一个 `ServerResponse`；
静态文件服务仍在旧链里，迁移时需注意 `res.writeHead` 与 `sendJson` 不混用。

# 前端自动保存

## 两种模式

| URL | 行为 |
|---|---|
| `/?flow=流程名.json` | 从内核加载，编辑后自动保存回去 |
| `/`（无参数） | 用内置示例数据（`initial-data.ts`），不保存 |

## 三处保存入口

| 位置 | 触发 |
|---|---|
| `use-editor-props.tsx` 的 `onContentChange` | 内容变更，防抖 1s |
| `save.tsx` 的 Save 按钮 | 手动 |
| `testrun-button` | 点 Test Run 前先存（不能跑旧图） |

## 数据覆盖 bug（已修，重要）

**现象**：拖动节点 → 自动保存成功 → 刷新页面 → **磁盘被重置回初始位置**。

**原因**：画布初始化时会触发 `onContentChange`（把加载的数据当成「变更」），
用初始位置覆盖了磁盘上用户的改动。

**修复**（两道保险）：

```ts
// 1. 加载后 2s 内忽略自动保存（那是画布初始化，不是用户改动）
if (Date.now() - loadedAt.current < 2000) return;

// 2. 内容没变就不写盘（幂等，也挡住 toJSON 字段顺序抖动）
const snapshot = JSON.stringify(next);
if (snapshot === lastSaved.current) return;
```

**验证**：拖动 → 磁盘更新 → 刷新 → 磁盘保持不变。

## 前置：Test Run 必须先保存

`testrun-button` 在打开面板前 `await workflow.save()`。
否则用户在画布上改了节点，点 Test Run 跑的还是内核里的旧图。

## 类型检查（全项目统一 TS 6.0.3）

`packages/client/app` 已升级到 TypeScript `^6.0.3`，与 dsh 侧一致。

- 全量检查：`npx tsc -b tsconfig.host.json`（352 个 references，含 `client/app`）
- 前端单独检查：`cd packages/client/app && npx tsc --noEmit`
- `tsconfig.json` 需要 `ignoreDeprecations: "6.0"` 来消除 `baseUrl` 的弃用报错

> 历史坑：前端曾用 TS 5.9，与 dsh 要求的 6.0.3 不兼容，`ignoreDeprecations: "6.0"`
> 在 5.9 上报 `TS5103: Invalid value`。统一版本后该问题消失。

## 失效模式

| 现象 | 原因 |
|---|---|
| 刷新后改动丢失 | 抑制窗口或内容指纹失效 |
| Test Run 跑的是旧图 | 没在打开面板前 `await save()` |
| 保存一直失败 | 内核未启动，或数据目录不可写 |
